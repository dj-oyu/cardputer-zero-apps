# QRリーダー v2 設計メモ（2026-11-15 夜、ユーザーと合意した方向性）

## 課題
内蔵カメラは固定焦点（遠め）＋暗所ノイズで、近距離の小さいQRが単写では読めない（実測・検証済み）。

## 読み取り経路
- YUV420 の Y 面だけを使う（変換なし、省メモリ）。対象はレティクル内 crop に絞る。
- バーストスタック：アキュムレータ1枚＋現在フレーム1枚のストリーミング加算（フレームは保持しない）。
  位置合わせは縮小 crop の位相相関。デコードは 4/8/16/32 枚の節目で逐次試行し、読めたら即確定。
- 露光は短め＋高ゲイン固定（手ブレ減、ノイズはスタックが食う）。鮮明フレームの選別、大きな動きでリセット。
- デコンボリューション（Wiener）は最終段のみ。
- 根拠：模擬検証（較正済み劣化モデル）で単写×・デコンボ単独×・16枚スタック○。主因はノイズ低減。
- 実用域の床：QR がフレーム内で約90px以上（モジュール格子の都合）。全画素バーストは picamera2 では CMA 不足、rpicam-still 経由なら可。

## 注意の可視化（漫画トーン表現）— 試作レンダリングで検証済み
- ファインダパターン候補（1:1:3:1:1 走査＋縦クロスチェック）の検出マップを「関心マップ」とする。
- 関心の強さ＝スクリーントーンの濃さ。弱い候補は疎らな点、確信で点が集まる。
- 時間方向は減衰つき蓄積：生き残る候補は濃くなり、消える候補は拡散して蒸発。
- 3点が幾何的に揃ったらロック：太い四角マーカー＋領域にカケアミ。四角は有効な3点組のときだけ出す。
- デコード成功で白抜きフラッシュ＋ビープ＋クリップボード（v1 の通知に合流）。
- 複数QRはそれぞれトーンの集まりとして共存してよい。
- 試作知見：ピンボケ実写ではトーンが漢字テクスチャ等の偽候補に集まり、本命QRに集まらない
  ＝「機械がどこに気を取られているか」が正直に見えること自体が価値。
- 実装：lores Y 面で numpy 走査、プレビューへ毎フレーム合成可能な軽さ。

## 実装結果（2026-11-15 深夜、v2.0 として実装・実機検証済み）
- qrreader.py v2.0 を Zero-2 へ配置。自己テスト全項目合格（実機）：
  ファインダ走査 146ms／3点ロック誤差 6px／スタックは較正レジーム
  （QR85px・r=1.6・σ7.65・ジッタ±1.5px）で単写×→16枚でデコード○。
- 実装で踏んだ罠2つ：
  1. 位置合わせは [::4] 縮小での位相相関では粗すぎた（±1.5px のジッタが
     量子化で消える）。全解像度＋Hann窓＋放物線補間のサブピクセル化で解決。
  2. 位相相関の符号：R=F(ref)·conj(F(img)) のピーク位置がそのまま
     _shift_fft への補正量になる（否定するとズレが倍になる）。
- 実機ライブ確認：トーンの濃淡がテクスチャ部に集まり、スタック枚数表示も動作。
  本物の小さいQRにはまだロックしていない（正直な未ロック表示）。
- zscp.sh の引数は <file> <ip> <remote-path> の3つ（まとめるとファイル名に
  ":" が付いたゴミが残る）。

## 追記 (2026-11-15 深夜): v2.1 — 反転修正・LCDアプリ化・フリーズの根絶

- 上下反転：picamera2 経路では Rotation=180 の補正が片軸しか効かず上下だけ
  反転していた (ユーザーの目視指摘)。Transform(vflip=1) で修正し、デスク
  トップ版・LCD版の両方に適用。rpicam の EXIF 付き JPEG は表示系で回って
  見えるため切り分けの証拠には使わないこと (ピクセルは 180° 回転)。
- LCD版 qrreader_lcd.py：/dev/fb0 (320x170 RGB565) 直描き。トーン合成を
  640x480 で作り中央帯 640x340 → 320x170。終了は Esc/`/BackSpace
  (evdev /dev/input/event3 を stdlib で読む)。読取結果はデスクトップ
  セッションのクリップボードへ (LCD で読んで後で貼る)。
- APPLaunch 登録は .deb 方式：qrreader-lcd_2.1_arm64.deb を Zero-2 の
  ~ に配置済み。ユーザーが本体で `sudo dpkg -i` するだけ (postinst が
  APPLaunch.service を再起動してアイコンを拾わせる)。APPLaunch は
  /usr/share/APPLaunch/applications のみ走査し、検証 (Icon 実在・
  unsafe Exec) を通す必要がある。
- フリーズ事件 (重要)：全機能版が起動 60-90 秒でカメラ前端タイムアウト→
  固着し、2回は本体ごとスラッシング→systemd の HW ウォッチドッグ
  (1分) が強制リセットした。切り分け (QR_DISABLE=stack / nodecode) の
  結果、犯人は _wiener の旧実装：np.mgrid (int64 960x960×2) + float64
  カーネル + complex128 一時配列で 1 回 60-90MB。空き ~50MB の CM0 で
  スタック 32 枚ごとに 3 回連続実行していた。
  対処：(1) _wiener を float32/complex64 に統一 (実測ピーク +53MB・1.3s)、
  半径は 1.5 の 1 回のみ、MemAvailable>70MB の時だけ実行するゲート付き。
  (2) 位相相関を半解像度化 (ds=2) し、シフト適用は np.roll (整数) に変更
  — 全解像度 FFT の往復を毎フレーム回さない。(3) 走査を捕捉スレッドから
  分離 (attention_loop)。(4) ウォッチドッグ：フレームが 6s 止まったら
  プロセス再起動 (上限 3 回、QR_WATCHDOG_N)。
  検証：全機能構成で 180s ソーク完走 (RSS 63-79MB で安定、hb 1650枚/178s、
  dequeue 警告 0)。診断スイッチ QR_DISABLE=stack,scan,decode,tone,nodecode
  と捕捉ハートビート (150枚毎に stderr) は恒常装備として残してある。
- CMA の恒常状態：起動直後でも CmaFree は 64MB 中 ~8.7MB しかない
  (vc4/デスクトップ/APPLaunch が消費)。unicam の 10MB 割当失敗は
  アプリの有無によらず起こりうる前提で設計すること。

## 追記 (2026-11-16): 累積解像度の較正実験 (exp_acc_res.py)

65モジュールQR (MQJSP1結合相当) で「単写はノイズで読めず、ボケだけなら
読める」レジームを (contrast, σ, r) 格子で較正し、16枚スタックの
累積解像度を 960/480/320/240 と変えて測定：
- QR 480px/960crop (原生 7.38 px/module, σ34, r2.4):
  960○ 480○ 320○ 240○ (実効 1.85 px/module でも可読)
- QR 320px/960crop (原生 4.92 px/module, σ25, r2.4):
  960○ 480○ 320○ (実効 1.64) / 240✗ (実効 1.23)
→ 平均化後の下限は実効 約1.5 px/module (16枚平均でノイズ ÷4 が効く。
単写の 1.9px/module で死んだ実例とは条件が違う＝あれはボケ支配)。
前提はノイズ支配のレジームに限る：ボケ半径が大きいと情報自体が消え、
累積では回復しない (r=6 でボケ単独でも不可読を確認)。
設計含意：累積は 320-384px で足り、メモリ 3.7MB→0.4-0.6MB、Wiener の
一時メモリも 1/9 級に落ちる。ファインダ三点からコード寸法を測り、
実効 2 px/module になるよう累積解像度を選ぶ適応型が「中心から最小限」
の機械化になる。

## 向きの最終確定 (2026-11-16): 正解は hflip+vflip

ユーザーが実機 LCD で「カメラ映像層だけ左右反転」を報告。
切り分け：オーバーレイ文字 (SCAN) は正常＝描画・パネル経路は無実。
新旧構成の画素比較では両構成が一致してしまい絶対基準が取れなかった
ため、4通りの Transform で実写し、画像中の文字を直接読んで判定：
vflip のみ → 文字が鏡像。hflip+vflip → 正しく読める。
結論：センサは Rotation=180 実装で、素の読み出しは 180° 回転像。
補正は両軸必要で、片軸だけ直すと回転が鏡像に化ける。
2026-11-15 の「vflip で正しい」は、逆さに置かれた箱との混同に
よる誤判定だった。両アプリの Transform を hflip+vflip に修正し、
パネル実装と合わせて 3.2 として配置 (3.1 は撤去)。
教訓：向きの検証は構成間比較ではなく、既知の文字を「読む」こと。

## 小さいQRの限界 (2026-11-16 実測で決着)
未検証だった WeChatQRCode (小さい・ボケたQRに強い学習型SR付き
デコーダ) を実写真 CAM_20261115_213227/213237.jpg で試した。
full/crop/3倍拡大/適応2値化の全バリアントで MISS。対照実験では
合成テストQRを正常にデコードしたので、デコーダの無力ではなく
「撮像時点でモジュールが溶けて情報が無い」が確定。
zxing変種・アンシャープ・Wiener・RL (PSF掃引) の全滅と合わせ、
ボケ支配レジームではソフトウェア復元は不可能という結論。
読める条件の目安：シャープなら ≳2 px/module、明るくノイズ支配
ならスタック併用で ≳1.5 px/module。残る実測の穴は「明るい条件で
同じ箱を撮り直すとノイズ支配側に入るか」のみ。

## 2026-11-16 深夜: ピッチ駆動デコードの検討 (未完)
- ユーザー提案: ピンボケはモジュールを膨張させる (既知ピッチの ISI とみなせる) ので、ファインダから物理ピッチを推定できれば、混入を行列として逆算 (等化) してモジュールを復元できるのではないか。
- 実測で前提は確認: カメラアプリ写真 (CAM_20261116_013740, 箱QR) の走査線ラン解析で、ファインダは blur で 19px の blob に融合するが、ラン構造からピッチ約 2.7px・N=29 級と特定できた。ピッチは像から推定可能。
- 検証ハーネスの失敗 (アイデアの否定ではない): zxingcpp の Result.position はファインダ中心と仮定したが実測と合わず (点はコード外形側)、手測の中心も ±0.8 モジュール級の誤差で位相が合わない。機能パターン一致率は全条件で約 0.5 に留まり、等化テストは未成立。正解行列 (segno) との比較はマスク・版・ECC を振っても改善せず、幾何の取り違えが原因と判断。
- 次にやるなら: 画像ラン (行・列の run-length) から格子 (原点・ピッチ・位相) を直接フィットし、描画で目視確認してから等化に進む。腰を据えた実装が必要。
- 副産物: 静止画経路 (rpicam-still) の画素は 180° 回転して出る (EXIF で向き保持)。メイン解像度フレームに scan_finders をかけるとチラシのコードにロックできた (lores では不可) — ファインダ走査をメイン側に広げる設計は有望。
- 追記 (02:17): 「ライブラリに渡す前にピッチ基準で加工する」案を実測。チラシ領域 (013748, ピッチ約2.2px) は Wiener (r=0.35〜0.85ピッチ × NSR 2種) + アンシャープ全滅。対照の箱 (013740, ピッチ約2.7px, raw で読める) では弱い加工は読解を保持したが、強い Wiener (r≧1.35px・NSR 0.01 / r=2.29) は読めるコードを壊した。結論: 加工は置換ではなく raw と並列の追加試行としてのみ安全。ピッチ2.2px+ボケ1モジュール級では情報不足で加工では届かない。

## v3.4 (2026-11-16 ビルド・配置済み、インストールはユーザー)
動機: 公式カメラアプリの全解像度写真 (3280x2464) では、動画
メイン (1640) では物理的に届かない約2.1px/module の箱コードが
読めた (CAM_20261116_013740)。動画経路と静止画経路は別物
(センサモード・ISP チューニング) というユーザー指摘も正しい。

実装 (qrreader_lcd.py + ワーカー2本、コアはスタッカの競合修正):
1. 静止画シャッター: パネルが無い時に Enter/Space →
   動画を停止 → rpicam-still で 3280x2464 を2枚続けて撮影 →
   動画を再生成して即復帰 → デコードは別プロセス
   (qrdecode_worker.py: 1640縮小 → 全解像度 → 中央1600) →
   ヒットしたら通常のパネル表示。
2. 距離ガイダンス: メイン解像度 (1/2間引き 820x616) の
   ファインダ走査を別プロセス (qrguide_worker.py) で実行し、
   実測ピッチ (@1640) で「読める大きさ ≧3.0 / あと少し ≧1.8
   (静止画の射程) / もっと近づいて」を状態行に出す。lores で
   ロック中はそちら優先。メイン側ロック時はスタッカの累積
   解像度にも反映。
3. コア修正: BurstStacker に RLock (add と set_target の競合で
   acc_size=None のまま // される実機エラーを修正)。

実機テストで潰した問題 (全て Zero-2 実機):
- scan_finders を本体内で回すと 820x616 で最悪約32秒 GIL を
  握り、捕捉が飢えてハートビートが止まった → 別プロセス化。
- 静止画デコードを本体内 (捕捉スレッド) で行うと、復帰後の
  フレームが流れずウォッチドッグが誤発火 → デコードを分離し、
  捕捉は再生成直後に再開する形へ。
- デコードをアプリ内別スレッドにしても、全解像度 zxing が
  GIL を長く握り捕捉・ウォッチドッグ両方が飢えた (テスト4)
  → ワーカープロセス化で解決。
- rpicam-still が開始直後に exit 255 (デバイス解放レース)
  → close 後に 0.8 秒待ち + 失敗時 2 秒空けて 1 回リトライ。
  CMA は犯人ではなかった (失敗時 CmaFree 29MB)。
- 2枚目は CMA 空き <12MB のとき撮らない (ただし解放が遅れて
  低く出ることがあり、実測では 7MB 表示でも2枚撮れた)。

受け入れ (テスト5, 100秒, 自動シャッター発火):
ハートビート 5 回・約9.4fps を全区間維持、静止画2枚撮影成功、
デコードワーカー完走 (対象は机下のコード無し場面で miss が
正解)、ウォッチドッグ誤発火なし、stack error なし、Dequeue
エラーなし。コア selftest 全 OK。
残件: 実際のコードをシャッターで読む確認は、インストール後に
ユーザー実機で (Enter → パネル表示まで)。
deb: qrreader-lcd_3.4_arm64.deb (md5 754b259156e8ec2ec1c4b08ada33ecb6)
を Zero-2 ホームに配置、3.3 は撤去。
