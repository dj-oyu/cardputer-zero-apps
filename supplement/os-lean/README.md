# Cardputer Zero OS 軽量化メモ（WIP）

公式イメージを別コピーで軽量化し、内蔵LCDのAPPLaunchとHDMIの利用可能性を残すための実験記録。**現時点でワンコマンドの再現手順ではない。** 対象の公式イメージは Debian 13.7 / aarch64、pi-gen stage4、参照日 2026-09-29。公式入手先は [M5Stack CardputerZero 使用ガイド](https://docs.m5stack.com/en/compute/cardputerzero/usage) の書き込み手順を参照。別バージョンではパッケージ構成と依存関係が変わる。

公式イメージ・変更後イメージ・個人データはこのリポジトリに含めない。作業前に元イメージのSHA-256を控え、実験にはコピーを使う。比較基準の元rawは 7,415,529,472 bytes、SHA-256 `cc95c131e8f77d96d016fac22579fd0a08009e4b821fc4c543fa122fdda84f0f`。これは特定版の照合値で、最新の公式配布物すべてに共通するものではない。

機体別データの退避・移行と復旧の考え方は [移行手順](migration.md)、実機の起動・アプリ・RAM/swapの試験条件と限界は [検証結果](validation.md)。これらは選択可能な作業手順と実験記録であり、完成済みの自動ビルダーではない。

## 作業環境と安全な順序

1. LinuxまたはWSL上で、raw画像のコピーを用意。`sfdisk -d`、`fdisk -l`、`blkid` でMBRと各領域を確認し、まず読み取り専用で調べる。実機用のSDを作業中のrootfsとしてマウントしない。
2. 基準版はbootがoffset 8,388,608 bytes / 512 MiB、root ext4がoffset 545,259,520 bytesから。**値を固定して他のイメージに適用しない。**
3. ARM64 rootfs操作は実機と同じDebian 13環境を優先し、サービス起動を抑止した隔離環境で行う。パッケージ削除はまず `apt-get -s purge ...` で削除対象と依存を確認。`autoremove` を無条件で実行しない。デスクトップ、カメラ、Wi-Fi、Bluetooth、APPLaunchとHDMIに関係する依存を確認する。
4. 作業後は `dpkg --audit`、`apt-get check`、アンマウント後の `e2fsck -fn`、アプリのselftestとrender-testで確認。OS上のユーザーがまだ存在しないとき、アプリのpostinstが警告を無視して成功することがあり、ランチャー登録の実機確認が別途必要。
5. 実機に書き込む前に画像を保持し、対象ディスクの識別・容量を確認。書き込み後は画像範囲全体を読み戻してハッシュ比較。初回設定、内蔵LCD、HDMI、Wi-Fi、Bluetooth、カメラとアプリを実機で確認する。

## 削減内容

検討・試験した候補は `packages-considered.txt`。各項目は特定版での実験結果であり、すべてを他版でそのままpurgeする指示ではない。例としてChromium / Firefox / VLC / 追加CJK字重 / 別ベンダーの外付け無線ファームウェアを除いた。ブラウザ、動画再生、該当USB無線、フォント字重などが失われる。Vulkan / Mesa / LLVMは描画やアプリに関係するため保持した。NFSとAvahiの停止はmDNSなどに影響する。

boot設定の `gpu_mem=128` を `64` にする候補と、HDMIデスクトップの自動停止を試験。後者は初回設定後のみ、APPLaunchの稼働確認と復旧手段を前提とする。初回LaunchWizard、ユーザー作成、lingerとAPPLaunchの有効化を守ること。デスクトップ停止中はHDMI画面が黒くなる。必要時に起動し直せる機構が必要で、実装はまだこのメモに含まない。

## 画像長と初回拡張

ファイル削除だけではraw画像の長さは縮まらない。元画像と別コピーで `e2fsck` → `resize2fs -P` → 安全余裕を持った `resize2fs` → `e2fsck -fn` を行い、パーティション終端をファイルシステム以上に設定した後、画像末尾を切る。MBRの開始位置・サイズ・ディスクIDとboot/rootのPARTUUID整合性を必ず確認する。縮小済みファイルと元の内容・権限・リンクなどは読み取り専用で比較する。

基準版での一例は ext4 1,470,000 × 4096 bytes、root開始545,259,520 bytes、全体6,566,379,520 bytes。別の状態ではサイズを再計算する。公式initramfsの `resize` 起動引数は初回に第2パーティションとext4を拡大し、PARTUUIDを更新して引数を消す。拡張処理・ユーザー作成・実機での初回起動は別々に確認する。

## 実測と未解決

試験機・HDMI未接続・LightDM停止・APPLaunchとネットワーク稼働時の一例は、OS認識RAM約415 MiB、利用可能RAM約233 MiB。zramが有効で、SD上のbacking fileを使う設定もある。プロセスPSSの合計はメモリ全体ではなく、ファイル由来PSSの全額がプロセス停止時に回収されるわけでもない。

段階的な匿名メモリ確保では、圧縮しにくいデータ269 MiBを確保し、利用可能RAMの観測値が約16.8 MiBまで下がった。その後ADBが十数秒以上停滞したため中断した。圧縮しやすいデータの別試験では456 MiBを確保し、swap空きの保護条件で停止した。負荷条件によって差が大きく、どちらもアプリの確実な上限ではない。経過、swap消費、未検証範囲は [検証結果](validation.md) を参照。CMA空きの瞬間値だけでカメラの可否は判定できない。

更新試験ではproot内のAPT権限切替が署名検証に失敗し、隔離環境で `APT::Sandbox::User=root` にすると署名検証を維持して取得できた。ただし `initramfs-tools` の処理がsysfs不在と一時ファイル参照で失敗し、生成物は信用できなかった。元カーネル・元initramfsを比較して戻した。署名検証を無効にしない。オフラインでの安全な自動再生成は未解決。

追試では、試験SDで実機を起動してから `update-initramfs -u -k "$(uname -r)"` を実行すると成功し、bootパーティションにも更新が反映された。再起動後のAPPLaunchとネットワークを確認。生成済みファイルの内容をrootfsとbootパーティションに反映する場合は、対象カーネルの版と実機構成の一致が必要。オフラインでの安全な自動再生成は引き続き未解決。

## 移行と個人情報

アプリ・依存は再現可能なパッケージとして別途選び、必要な個人データは利用者がオフラインで移行する。Wi-Fi・Bluetooth・SSH・Tailscaleの状態、鍵、ユーザーデータ、ホストIDは公開画像・ログ・リポジトリに入れない。機器間で認証状態を複製するとIDが衝突するため、別の機器に流用しない。設定ファイルの移行では所有者・権限・リンクと初回設定フローを確認する。
