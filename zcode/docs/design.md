# zcode 設計

CardputerZero（CM0、320×170 液晶、tca8418 キーボード）で動く、VS Code 風の
コードエディタ。Rust で書く。画面と操作は `ui-mock.html` に従う。
この文書は実装担当（人・エージェント）への指示書を兼ねる。担当は自分の節と
「共通の約束」を読めば作業できるようにしてある。

## 1. 目標

| 項目 | 目標 |
|---|---|
| 打鍵 → 液晶への転送開始 | 中央値 10ms 以下、p95 16ms 以下 |
| スクロール 1 画面 | 転送開始まで 12ms 以下、転送完了まで中央値 30ms 以下（全画面の転送だけで約 17ms かかる） |
| 起動 → 最初の画面 | 200ms 以下 |
| 常駐メモリ (RSS) | 30MB 以下（SKK 辞書・フォントは mmap でページキャッシュ扱い） |
| 待機中の CPU | 0%（入力もタイマーも無ければ眠る） |

## 2. 実機で測った前提（2026-11-16）

要点だけを書く。測り方・条件・全部の数字は `measurements.md`、測ったプログラムは
`../bench/` にある。

**液晶**（ST7789V、SPI 60MHz、ドライバは panel-mipi-dbi-spi＝DRM の fbdev
エミュレーション。fb0 への書き込みは遅延 I/O でまとめて転送される）

- 書いただけだと、転送開始まで **中央値 30ms・最大 56ms**（約 50ms 周期）
- 書いた直後に `fsync(fb0)` すると、転送開始までの待ち（中央値 / p95）は
  **1 行 1.5 / 5.2ms、13 行（テキスト 1 行分）4.6 / 6.5ms、全画面 9.6 / 12.2ms**。
  行数にほぼ比例する（約 50µs/行）
- `fsync` 自体はふつう 0.06〜0.2ms で返り、転送の完了を待たない（転送は
  カーネルのワーカーが別コアで行う）。ただし **直前の `fsync` の直後に続けて呼ぶと
  止まる**: 直前が 1 行なら 0.7ms、13 行なら 1.1ms、全画面なら 7.1ms。1ms 以上
  あければ止まらない
- 転送範囲は「変更されたページ全体を含む **1 つの行範囲**（横は常に全幅）」。
  離れた 2 か所を変えると、その間も全部送られる
- 全画面（108,800 バイト）の転送は実効約 50Mbit/s で **約 17.4ms**（2 回に分かれる）。
  `fsync` から転送完了まで中央値約 27ms。全画面の書き込みと `fsync` を連続で
  呼んでも、カーネルが最新の内容にまとめるので溜まらない
- mmap への書き込みは、転送中でも止まらない（最大 0.15ms 程度）

**CPU とスレッド**

- Cortex-A53 ×4、ondemand 600MHz〜1GHz。**負荷がかかってから 1GHz に上がるまで
  100ms**（sampling_rate）、上がると 1〜5 秒保つ。100ms 未満で終わる処理と、
  打鍵ごとの処理は 600MHz で走る前提にする
- 全画面の文字合成（13 行 × 53 字）は 600MHz で 370µs、1GHz で 222µs。
  行差分は約 0.1ms、全画面のコピーは 0.03〜0.1ms、memmove スクロールは 43µs
- メモリ帯域は 1 コアで飽和する（大きなコピーは 4 スレッドでも 0.92 倍）。
  DFA の表引きは 4 スレッドで約 4 倍、文字合成は約 2.3 倍
- スレッド間の受け渡し（eventfd で起こして poll で受ける）は往復 50〜90µs。
  スレッド生成は 1 本 0.13〜0.34ms、メモリ +29KB
- `RLIMIT_RTPRIO=0`、`RLIMIT_NICE=0`: リアルタイム優先度も負の nice も使えない。
  ワーカーの優先度を下げる方向だけ可能。コア固定の効果は無かった

**SD カード**

- mmap したファイル（フォント・SKK 辞書）の初回アクセスは、SD からの読み込みで
  **1 回 5〜16ms 止まる**（初めて描く漢字 300 字で合計 302ms）
- `~/.cache` への 64KB の書き込みは write 0.55ms、**fsync 9.5ms**（最大 12.3ms。
  静かな状態での値で、実際はもっとばらつく）
- `mincore` で常駐ページを確かめる方法は使えない（自分が持ち主でないファイルは
  常に「常駐」と返る）

**その他**

- APPLaunch はランチャー表示中も再描画している（SPI 2.6万〜35 万バイト/秒と
  状態で変わる、CPU 約 9%）。アプリ起動中に止まるかは段階 1 で確認する
- キーボード: **キーリピートが無い**（EV_REP 無し）。Shift / Sym / Fn は
  ドライバが押下・ワンショット・ロックを管理し、キー配列を切り替えて送る
- メモリ: 見えるのは 352MB、デスクトップ常駐時の空きは 74〜117MB、zram スワップ使用中

## 3. 構成

Cargo ワークスペース。crate を分けるのは、担当を並行して作業させるためと、
UI に依存しない部分を単体テストできるようにするため。

```
zcode/
  Cargo.toml            ワークスペース
  crates/
    zc-core/            共通の型: Rect, Color(RGB565), Style, KeyEvent, Command, Damage
    zc-display/         fb0 出力・PNG 出力 (render-test)・行差分・フラッシュ計画
    zc-font/            フォント読み込み (mmap)・ラスタライズ・グリフキャッシュ・合成
    zc-input/           evdev 読み取り・grab・モディファイア・キー配列・自前リピート
    zc-buffer/          テキストバッファ (rope)・カーソル/選択・undo・変更通知
    zc-highlight/       言語登録・ハイライト (ビルド時に DFA 化)・行単位の状態キャッシュ
    zc-intel/           単語補完・構文チェックの実行・アウトライン (§10)。後の版で LSP クライアント
    zc-markdown/        Markdown の解析とライブプレビューの行レイアウト
    zc-skk/             SKK エンジン (UI 非依存)・辞書 (mmap 二分探索)
    zc-term/            pty・端末エミュレーション (vte)・スクロールバック
    zc-ui/              画面部品 (タブ・ツリー・エディタ・パネル・ステータスバー・一覧)
    zcode/              main: イベントループ・コマンド表・設定・保存
  languages/            言語定義 (§7)。ここにファイルを足すだけで言語が増える
  keymap/               キー配列の対応表 (キー確認モードの結果)
  tests/golden/         render-test の正解画像
```

依存の向き: `zc-core` ← 各 crate ← `zc-ui` ← `zcode`。横同士は依存しない
（例: `zc-skk` は `zc-buffer` を知らない。確定文字列を返すだけ）。

### 共通の約束

- 描画はすべて `zc_core::Canvas` に対して行う。fb0 も PNG も同じ `Canvas`
  （RGB565 の 320×170 配列）なので、**実機が無くても render-test で確認できる**
- 各部品は `fn render(&mut self, canvas: &mut Canvas, area: Rect) -> Damage` を
  持ち、自分が描き変えた行範囲だけを返す。何も変わらなければ空を返す
- 操作はすべて `Command`（列挙型）で表す。キー割り当てとショートカット一覧は
  `zcode/src/commands.rs` の **1 つの表** から作る（一覧だけ古くなるのを防ぐ）
- I/O（保存・fsync・辞書書き込み・子プロセス待ち）はイベントループで待たない。
  ワーカースレッドに投げ、結果は eventfd で受ける（スレッド構成は §4）
- **SD から読み込みが起きうる mmap（フォント・SKK 辞書）に、メインスレッドで
  触らない**（1 回 5〜16ms 止まる）。assist スレッドに頼む
- **`fsync(fb0)` はメインスレッドで呼ばない**（続けて呼ぶと最大 7ms 止まる）。
  flush スレッドが呼ぶ
- C ライブラリに依存する crate は使わない（クロスビルドを軽く保つ）
- 各 crate は `cargo test` が通り、UI 部品は render-test の正解画像と一致すること

## 4. イベントループとスレッド構成（`zcode`）

### 4.1 方針

描画の処理そのもの（文字合成・行差分・コピー）は **並列化しない**。全画面でも
1 スレッドで 0.4〜0.7ms（600MHz）しかかからず、並列化しても 0.1ms 程度しか縮まない。
打鍵の遅延を決めているのはカーネルの転送開始待ちと SPI 転送で、こちらは並列化で
縮まない。マルチコアは **「メインスレッドを待たせない」ためだけに使う**
（fb0 の fsync、SD からの読み込み、SD への fsync、重い一括処理）。

### 4.2 スレッド

メイン 1 本と、常駐ワーカー 4 本（増えるメモリは約 0.3MB）。ワーカーは条件変数か
poll で眠るので、待機中の CPU は 0% のまま。assist と batch は最初の依頼で作る。

```
              ┌──────────── メイン（poll: evdev / pty / timerfd / eventfd）────────────┐
              │ 入力 → 編集 → 見えている行のハイライト → 描画 → 行差分                 │
              └──┬──────────────┬────────────────────┬──────────────────┬─────────────┘
       Mutex＋条件変数         mpsc                  mpsc               mpsc
   (提示用バッファ＋行範囲)  (字, サイズ, 版)   (rope の写し, 版)    (保存の依頼)
                 ▼              ▼                    ▼                  ▼
              flush          assist                batch             storage
          fb0 書き込み     字形のラスタライズ    ファイルを開く       一時ファイル
          ＋ fsync          SKK 辞書の探索        ハイライトの残り     → fsync → rename
                                                  Markdown 全体の解析   控えの書き出し
                                                  検索・構文チェック
                            └───────────┬──────────┴──────────────────┘
                                        ▼
                   結果は mpsc ＋ eventfd 1 本でメインへ（版が古ければ捨てる）
```

| スレッド | 持ち物・仕事 | 優先度 |
|---|---|---|
| メイン | 入力（evdev を直接読む）、キーリピート（timerfd）、編集、SKK の状態機械、見えている行のハイライト、描画、行差分、pty の読み取りと端末の解釈 | 既定 |
| flush | fb0 の mmap と fd。`fsync(fb0)` を呼ぶのはここだけ（§5.1） | 既定 |
| assist | キャッシュに無い字形のラスタライズ、SKK 辞書の探索（mmap に触る仕事） | 既定 |
| batch | ファイルを開く（読み込み・rope 構築・行頭状態の計算まで）、ハイライトの残り、Markdown 全体の再解析、追加言語のコンパイル、検索、構文チェックの子プロセス | nice +10 |
| storage | 保存（§8）。1 本で直列に処理し、同じファイルへの依頼は最新だけ残す。終了時は join して書き切る | nice +10 |

- **古い結果の扱い**: batch への依頼には、ropey の clone（中身は共有なのでコピー
  しない）と版番号を付ける。batch は `AtomicU64` の現在の版を数百行ごとに見て、
  古ければやめる。メインも、版が違う結果は捨てる
- キー入力をワーカーに渡すことはしない（受け渡しの 30〜55µs が乗るだけ）
- コア固定はしない（効果が無かった）。優先度は上げられないので、batch と storage を
  下げる

### 4.3 メインのループ

`poll()` で次を待つ:

- evdev（キーボード）
- pty の master（ターミナル出力）
- timerfd（キーリピート・カーソル点滅・控えの保存・ステータスバーの遅延更新）
- eventfd（ワーカーからの完了通知。1 本にまとめる）

起きたら **溜まっている入力を全部処理してから 1 回だけ描く**。打鍵が速くても
描画は打鍵の数だけ増えない。ターミナル出力は 1 回の起床で読む量に上限
（64KB か 2ms）を設け、先に入力を見る。大量に流れるときは、描画を
最短 33ms 間隔（30fps）に間引く。

## 5. レンダリング（`zc-display`, `zc-font`, `zc-ui`）

### 5.1 フレームの流れ

1. （メイン）各部品が裏バッファ（`Canvas`）の自分の領域に描き、変えた行範囲を返す
2. （メイン）`zc-display` が裏バッファと提示用バッファ（108KB）を行ごとに比べ、
   変わった行だけを提示用バッファにコピーし、優先度つきの行範囲リストに足して
   flush スレッドを起こす（ここまでで 0.03〜0.1ms）
3. （flush）範囲を 1 つずつ取り出し、fb0 の mmap に書いて `fsync(fb0)` する
   （約 50ms の待ちを消す）。続けて fsync すると止まるが、止まるのは flush だけ
4. flush が忙しい間にメインが同じ行を書き換えたら、範囲を併合する。液晶には
   常に最新の内容だけが出る

### 5.2 転送範囲を小さく保つ（フラッシュ計画）

ドライバは変更範囲を **1 つの行範囲に丸める**。編集中の行（上の方）と
ステータスバー（最下段）を同時に変えると、間の 100 行以上も送られて約 10ms 余計に
かかる。転送開始までの待ちも行数に比例して伸びる（約 50µs/行）。そこで:

- 変わった行範囲が離れているときは、flush スレッドが **範囲ごとに書いて fsync を
  分ける**（近いものはまとめる。目安: 間が 20 行未満ならまとめる）
- ステータスバーの行・桁表示は、打鍵の直後ではなく 50ms 静かになってから更新する
  （打鍵の遅延に乗せない）
- 優先順: カーソル行 → 編集範囲 → その他 → ステータスバー

### 5.3 スクロール

- 裏バッファの行を memmove でずらし、新しく見えた行だけ描く（CPU は軽い）
- 転送はほぼ全画面になる（約 17.4ms、fsync から完了まで中央値約 27ms）。
  なめらかなスクロールアニメーションはしない（1 回で動かす）
- **スクロールのキーリピートは 1 秒 20 回**にする（30 回では毎回の全画面転送が
  間に合わない）。それでも追いつかなければ途中の位置を飛ばす

### 5.4 文字の描画

- フォントは mmap して必要な字形だけ取り出す（`swash`。DejaVu Sans Mono は
  TrueType のヒンティングが効くので、小さい文字もにじみにくい）。全字形を最初に
  読み込むライブラリは使わない（Noto Sans CJK は 1 書体で約 20MB ある）
- フォールバック順: DejaVu Sans Mono → Noto Sans Mono CJK（日本語）→ 記号用
- ラスタライズした字形は 8bit の濃度で LRU キャッシュ（上限 512KB。漢字 1 字
  約 140 バイトなので 3,000 字以上入る）。キャッシュはメインだけが持つ
- キャッシュに無い字は assist スレッドにラスタライズを頼み、**最大 2ms だけ待つ**。
  フォントのページが RAM にあれば 0.1ms 程度で返る。間に合わなければ空白で描き、
  完了通知が来たらその行だけ描き直す（SD からの読み込み 5〜16ms をメインで踏まない）。
  実測: ASCII 1 字 26µs、漢字 1 字 66µs（RAM にあるとき）
- 合成は、背景色と文字色の組ごとに **16 段階の色の表**（RGB565）を作り、
  濃度を 4bit に丸めて表を引くだけにする（1 画素ごとのアルファ計算をしない）
- 斜体は字形を傾けて合成する（CJK に斜体の字形が無いため）
- ビットマップフォント（東雲 12px など）の方が読みやすい可能性がある。段階 1 で
  実機に並べて比べ、良ければ `zc-font` に BDF 読み込みを足す（ライセンス確認込み）

### 5.5 可変の行高と字幅

Markdown のライブプレビューでは、見出しは大きく本文はプロポーショナルになる。
エディタの表示は最初から「論理行 → 表示行（高さ・各文字の x 座標）」の
レイアウト結果を持つ形にし、等幅のマス目を前提にしない。コード表示は
「全部の行が同じ高さ・同じ字幅」という特別な場合として同じ仕組みで扱う。

## 6. 入力と遅延（`zc-input`）

### 6.1 打鍵から液晶までの内訳（目標）

| 区間 | 見込み |
|---|---|
| キー押下 → evdev イベント（I2C 読み取り・ドライバ） | 1〜3ms（段階 1 で計測） |
| poll から起きて処理・1 行描画・行差分（600MHz） | 0.1〜0.7ms（実測。全画面でも 0.7ms） |
| flush スレッドへの受け渡し | 0.05〜0.09ms（実測） |
| fb0 書き込み → `fsync` → 転送開始（13 行） | 中央値 4.6ms / p95 6.5ms（実測） |
| 13 行分（約 8KB）の SPI 転送 | 約 1.3ms |
| **合計** | **約 7〜11ms**（fsync 無しだと 35〜65ms） |

CPU は ondemand で、1 打鍵の処理は 600MHz のまま走る（1GHz に上がるまで 100ms
かかる）。600MHz でも十分軽いので、ガバナは触らない（電池優先）。重い処理
（ハイライトの残りなど）は batch に回す。

### 6.2 キーの扱い

- evdev を直接読む。**キーボードは独占しない**（段階 1 で確認）。APPLaunch は
  アプリの起動中、自分のキー処理を止めてキーボードを共有し、Esc の約 3 秒長押しで
  アプリのプロセスグループに SIGTERM → SIGKILL を送る（本体共通の強制終了）。
  独占するとこれが効かなくなる。`--grab` は SSH から試すとき専用
- Esc の長押しは操作に割り当てない。SIGTERM を受けたら、未保存の内容の控え（§8.4 の
  段 1）を書いてから終わる（SIGKILL までの猶予は短いので、控えは RAM の tmpfs に書く）
- **画面のスリープは zcode の役目**（APPLaunch はアプリの起動中にタイマーを止める）。
  ランチャーの設定 `dark_time`（`~/.config/cardputerzero/config.json`、既定 30 秒、
  0 は眠らせない）だけ打鍵が無ければバックライトを消し、描画も止める。打鍵ごとに
  1 回だけ鳴るタイマーを先へ延ばすだけで、見張りのポーリングはしない。消えている間の
  打鍵は画面を起こすだけで、アプリには渡さない（そのキーのリピートと離上も捨てる）。
  起こすときの明るさはランチャーの設定 `brightness`
- 1 回起きたら読めるイベントを全部読む。`SYN_DROPPED` が来たら押下状態を
  `EVIOCGKEY` で取り直す
- **キーリピートは自前で作る**: 押下から 400ms 後に開始、以後 30 回/秒
  （画面がスクロールする操作は 20 回/秒。§5.3）。対象は文字・BackSpace・Delete・
  矢印・PgUp/PgDn。Ctrl の組み合わせはリピートしない（Ctrl+S の連打を防ぐ）。
  値は設定で変えられる
- キーコード → 文字の対応は `keymap/` のデータファイルから読む。Sym レイヤーの
  記号は、キー確認モード（`zcode --keytest`）で実機を押して確定させる
- 出力は `KeyEvent { key, mods, text: Option<char> }`。SKK・エディタ・
  ターミナルはこれだけを受け取る

## 7. ハイライト（`zc-highlight`）— 言語を足しやすく、実機で速く

### 7.1 方式の決定（2026-11-16 実機で比較）

| 方式 | 1 行あたり | 最初のハイライト | 起動時 |
|---|---|---|---|
| syntect（`.sublime-syntax` を実行時に正規表現コンパイル） | 約 1.8ms | 約 200ms 止まる | 全 75 言語の読み込み 6ms、Python を使うと +11MB |
| **独自の規則 → ビルド時に DFA 化して埋め込み** | **約 0.004ms** | 止まらない | 2.4ms、メモリ増加ほぼ 0 |

syntect のバイナリ形式は「規則の文字列を詰めただけ」で、正規表現のコンパイルは
実行時に起きる。A53 ではそれが重く（1 画面 13 行で約 25ms、1000 行で約 1.8 秒）、
打鍵の遅延目標（§1）に入らない。そこで:

- **元データはテキスト**（人が読んで直せる、差分が見える、リポジトリで管理する）
- **実機に配る形は、ビルド時に作った「そのまま実行できる」バイナリ**
  （正規表現を DFA＝状態遷移表に変換済み。実行時にはコンパイルもパースもしない）

### 7.2 言語の追加

**言語を 1 つ増やす作業は `languages/<言語>/` にファイルを置くだけ**。コードは変えない。

```
languages/
  python/
    language.toml   言語の設定と規則 (テキスト)
    sample.py       見本 (自動でテストされる)
  theme.toml        トークンの種類 → Dark+ の色
```

`language.toml` の例:

```toml
name = "Python"
extensions = ["py", "pyw"]
first_line = '^#!.*python'      # 拡張子が無いファイルを shebang で判定
line_comment = "#"              # Ctrl+/ のコメント切り替え
indent = "    "
run = "python3 {file}"          # F5 で実行するコマンド

# 文脈ごとに規則を並べる。上から順に試し、push / pop で文脈を出入りする
[[contexts.main]]
match = '#[^\n]*'
token = "comment"
[[contexts.main]]
match = '[rRbBfFuU]{0,2}"""'
token = "string"
push = "triple_dq"
[[contexts.main]]
match = '(?:def|class|if|else|for|return|import|from)\b'
token = "keyword"

[[contexts.triple_dq]]
match = '"""'
token = "string"
pop = true
[[contexts.triple_dq]]
match = '[^"]+|"'
token = "string"
```

- 規則の書き方は Sublime Text / TextMate の文法（文脈の push / pop）に寄せる。
  既存の `.sublime-syntax` から変換する補助ツール（`zcode-langc import`）を用意し、
  変換できない書き方は警告として一覧にする。残りは人かエージェントが直す
- 使える正規表現には制限がある（DFA にできないもの）: **後方参照・先読み・後読みは
  不可、`\b` は ASCII の単語境界**。ヒアドキュメントの終端一致のように後方参照が
  要るものは、エンジン側の特別な規則（`heredoc` など）で表す
- 非 ASCII の文字は「識別子の一部」としてまとめて扱い、Unicode の文字クラスは
  使わない（使うと Python だけで DFA が 1.26MB になった。1 言語あたり 100KB 以下が目安）
- `build.rs` が `languages/*/` を全部コンパイルし、**言語ごとに連続した領域**に並べて
  実行ファイルに埋め込む（形式は §8）。開いた言語の分しか SD から読まれない
- 実機の `~/.config/zcode/languages/` に置いた言語は、そのファイルを初めて開いたとき
  ワーカースレッドでコンパイルする（終わるまではハイライト無しで表示）。コンパイル
  結果は SD に書かない（§8）
- `sample.*` は自動テストの対象: ハイライト結果を正解
  （`tests/golden/highlight/<言語>.txt`）と比べる。正解が無ければ作って差分を見せる
- `language.toml` は F5 の実行コマンドとコメント記号も持つので、言語を足すと
  実行とコメント切り替えも同時に使えるようになる

### 7.3 実行時の動き

- 行ごとに「行頭の文脈スタック」を覚えておき、編集した行から下は、行頭の文脈が
  前回と同じになったところで再計算を打ち切る（DFA なので 1000 行でも数 ms）
- 見えている行と、編集した行から下の再計算は、メインで同期して行う（13 行で
  約 50µs）。1 回の予算（目安 2,000 行）を超える分だけ、rope の写しと版番号を
  付けて batch に出す（§4.2）。行頭の状態は前の行に依存するので、1 ファイルの中を
  分割して並列にはしない
- `zc-highlight` の外には「行 → 色付きの区間」の形でしか見せない。将来
  tree-sitter などに替えても、ほかの crate は変わらない

最初の版の言語: Python、Shell、Markdown、JSON、TOML、Rust、C。

## 8. データの持ち方（SD カード前提）

ストレージは SD カード。読み出しが遅いだけでなく、**書き込み寿命**がある
（内部では数 MB の消去単位で書き換えるので、小さな書き込みでも何倍にもなる）、
**書き込みの遅延がばらつく**（fsync が数十 ms〜、内部の整理中は秒単位もある）、
**電池切れで突然電源が落ちる**、という条件がある。

### 8.1 データの分類と持ち方

| データ | 読み書き | 形式 | 置き場所 |
|---|---|---|---|
| ハイライト規則・テーマ・キー配列・既定の設定 | 読むだけ | 実行できる形のバイナリ（§8.2） | 実行ファイルに埋め込み |
| SKK システム辞書・フォント | 読むだけ（大きい） | 元のファイルのまま | mmap で必要なページだけ |
| ユーザーの設定・追加した言語 | 読む（たまに人が書く） | テキスト（TOML） | `~/.config/zcode/` |
| 編集中のファイル | 明示的な保存のときだけ書く | 元のまま | 元の場所 |
| SKK 個人辞書 | 学習のたびに変わる | uim-skk と同じテキスト（EUC-JP。変えられない） | `~/.skk-uim-jisyo` |
| 未保存内容の控え・セッション（開いているタブ・カーソル位置） | 頻繁に変わる | 独自バイナリ（§8.3） | 2 段（§8.4） |
| ログ | 頻繁 | テキスト | RAM（tmpfs）だけ。SD には書かない |

### 8.2 読むだけのバイナリに求める性質

- **ゼロコピー**: 埋め込んだバイト列をそのまま使う（DFA の `from_bytes` 相当）。
  パースもヒープへのコピーもしない。だから起動が速く、RSS も増えない
- **局所性**: 言語ごと・用途ごとに連続した領域に置く。実行ファイルはページ単位で
  必要なところだけ SD から読まれるので、使わない言語のデータは読まれない。
  言語を開くときに `madvise(WILLNEED)` でまとめて先読みし、ばらばらの小さな読み出しを避ける。
  なお、ページが RAM にあるかを `mincore` で確かめる方法は使えない（自分が持ち主で
  ないファイルは常に「常駐」と返る）。読み込みが起きうる前提で、mmap にはメインで
  触らない（§3）
- **整列と固定のバイト順**: 4 バイト境界に置き、リトルエンディアン固定（aarch64）
- **版の検査**: 先頭にマジック・形式の版・ビルド ID。実行ファイルと一緒に配るので、
  互換性の心配は無い（版が違えばビルドの不具合として起動時に検出する）
- **実行時に作り直さない・キャッシュを SD に書かない**: 変換はビルド時に済ませる。
  「起動時にテキストから変換して SD にキャッシュする」形は、書き込みが増えるので採らない

### 8.3 書くデータに求める性質

- **書く回数を減らす**: 内容が変わっていなければ書かない（ハッシュで比較）。変更は
  まとめてから書く（最短間隔を決める）。1 つのファイルにまとめ、小さなファイルを
  たくさん作らない（作成・名前変更はジャーナルへの書き込みも増える）
- **小さなファイルは丸ごと書き直す**: 一部だけ上書きする形（ランダムな書き込み）より、
  小さく保って丸ごと順に書く方が SD に優しい
- **電源断に耐える**: 一時ファイルに書く → fsync → rename → ディレクトリを fsync。
  独自形式のファイルには、マジック・版・長さ・CRC32 を付け、途中で切れたファイルや
  壊れたファイルを見分けて読み飛ばす。1 世代前（`.bak`）を残し、壊れていたらそちらを使う
- **壊れていても止まらない**: 読めなかったら既定値で起動し、ステータスバーで知らせる
- **書き込みで画面を止めない**: fsync はいつもワーカースレッドで行う
- **ほかのアプリとの共存**: SKK 個人辞書は uim-skk も読み書きする。uim と同じ
  ロックファイル（`~/.skk-jisyo.lock`）を守り、書くときは丸ごと書き直す（uim と同じ）。
  学習のたびには書かず、5 分おき（変化があれば）と終了時に書く

### 8.4 控え（クラッシュと電池切れへの備え）は 2 段にする

| 段 | 置き場所 | 頻度 | 守れるもの |
|---|---|---|---|
| 1 | `/run/user/1000/zcode/`（RAM の tmpfs） | 操作が 2 秒止まるたび | zcode の異常終了。SD には書かないので何度書いても寿命に響かない |
| 2 | `~/.cache/zcode/`（SD） | 操作が 60 秒止まったとき・タブを切り替えたとき・電池残量が少ないとき | 電池切れ・電源断 |

起動時に控え（段 1 → 段 2 の順に新しい方）が見つかれば、復元するか尋ねる。
保存に成功したファイルの控えは消す。



## 9. その他の主要部品（要点）

- **zc-buffer**: `ropey`。編集は「変更された行範囲」を通知し、ハイライトと描画は
  それを見て無効化する。undo は操作単位でまとめる（連続入力は 1 単位）
- **zc-skk**: 状態機械（直接入力 / ▽ / ▼ / 登録）はメインで動く。`KeyEvent` を受けて
  「確定文字列・表示用の未確定文字列・候補一覧」を返す。辞書は EUC-JP を mmap して
  二分探索（`encoding_rs` で比較用に変換）。**辞書の探索は assist スレッドで行い**、
  かなモードに入った時点で辞書全体（4.4MB）に `madvise(WILLNEED)` をかけて先読み
  する。個人辞書 `~/.skk-uim-jisyo` は起動時に読み、変更は §8.3 の条件（ロック・
  5 分おきと終了時・丸ごと書き直し）で storage スレッドが書き戻す（uim-skk と同じ
  形式・同じ並び）
- **zc-markdown**: `pulldown-cmark` で解析し、行ごとに「装飾付きの区間・行の高さ・
  記号の位置」を返す。カーソル行だけ記号を表示する切り替えはここで行う。編集中の
  ブロックだけメインで解析し直し、全体の再解析は版番号付きで batch に出す
  （閾値は段階 5 で pulldown-cmark を実機で測って決める）
- **zc-term**: `rustix` で openpty・fork/exec、`vte` でエスケープシーケンスを解釈、
  画面とスクロールバック（1000 行）を持つ。読み取りと解釈はメインで行い、1 回の
  起床で読む量に上限（64KB か 2ms）を設ける。段階 3 で入力が遅れるようなら専用
  スレッドを検討する。子プロセスは `oom_score_adj` を上げ、メモリ不足のときに
  zcode より先に落ちるようにする
- **保存と控え**: §8.3・§8.4 のとおり（一時ファイル → fsync → rename を storage
  スレッドで。控えは RAM と SD の 2 段）

## 10. 補完・エラー表示・LSP（`zc-intel`）

### 10.1 実機で LSP を常駐させない理由（2026-11-16 計測）

| 項目 | 結果 |
|---|---|
| jedi 0.19.1（実機にある。python-lsp-server の中身）の読み込み | 1.3 秒、メモリ 25MB |
| jedi の補完 初回（`os.pa`・`np.ar`） | **8.5〜11 秒** |
| jedi の補完 2 回目以降 | 0.2〜0.6 秒 |
| jedi のメモリ | **約 60MB**（キャッシュ 6.3MB を書く） |
| jedi の構文エラー検出（1181 行） | 1.7 秒 |
| `python3 -I -S -c "ast.parse(...)"`（1181 行、起動込み） | **約 370ms**、ピーク 16MB、使い捨て |
| 実機の LSP サーバ・Node.js | どれも入っていない |

空きメモリ（70〜110MB）に対して jedi だけで 60MB を使い、zcode と並べると zram
スワップに追い出されて打鍵まで重くなる。pyright（Node.js）や rust-analyzer は論外。

### 10.2 段階的に入れる

| 版 | 機能 | 仕組み |
|---|---|---|
| **最初の版** | 単語補完 | 開いているファイルの単語と言語のキーワードから候補を出す（VS Code の既定の補完と同じ考え方）。DFA のトークンを使い回すので追加の処理はほぼ無い |
| | 保存時の構文チェック | 保存したら batch が `language.toml` の `check` コマンドを使い捨てで実行し、出力からエラー行を拾って波線を付ける（Python は `ast.parse`、約 0.4 秒） |
| | アウトライン | `def` / `class` などの行をトークンから一覧にする |
| 後の版 | 実機の LSP を必要なときだけ | Ctrl+Space を押したときに起動し、しばらく使わなければ止めてメモリを返す。候補は jedi-language-server、ruff server（Rust 製、リントと整形。実機では未計測）。どれも pip で入れる必要がある |
| さらに先 | Tailscale 越しに PC の LSP | PC で pyright などを動かして通信する。実機のメモリはほぼ使わないが、ネットワークがあるときだけで、実機にしかないライブラリ（`picamera2` など）は PC から見えない |

`language.toml` の例（追加分）:

```toml
check = "python3 -I -S -c 'import ast,sys; ast.parse(open(sys.argv[1]).read(), sys.argv[1])' {file}"
check_pattern = 'line (\d+)'     # エラー行を拾う正規表現
# 後の版
# lsp = "jedi-language-server"
```

`zc-intel` は「補完候補」「診断（行・桁・メッセージ）」「アウトライン」の 3 つの
形だけをほかの crate に見せる。最初の版の実装と、後の版の LSP クライアントは
その裏で差し替える。

## 11. 進め方と担当

### 11.1 段階

| 段階 | 内容 | 終わりの条件 |
|---|---|---|
| 1 土台 | ワークスペース、`zc-core` の型、スレッド構成（§4）、`zc-display`（fb0 / PNG・行差分・flush スレッド）、`zc-input` の最小版、キー確認モード、ビットマップ vs TrueType の比較画面 | 実機でキー確認モードが動き、モディファイアの送られ方と読み取りの遅延の実測が取れる。Sym の対応表はランチャーの表で確定（2026-11-16）。APPLaunch はアプリの起動中に再描画を止める（公式ソースで確認） |
| 2 エディタ | `zc-font`（assist スレッド込み）、`zc-buffer`、`zc-highlight`、`zc-intel` の最初の版（単語補完・構文チェック・アウトライン）、エディタ・タブ・ツリー・ステータスバー | Python を開いて編集・保存できる。打鍵遅延が目標内 |
| 3 ターミナル | `zc-term`、F5 実行 | 実行・停止・終了コード表示 |
| 4 SKK | `zc-skk`、未確定表示・候補一覧・登録欄 | 個人辞書が uim-skk と共有される |
| 5 Markdown | `zc-markdown`、ライブプレビュー・ソース切替 | モック 10・11 と同じ見た目 |
| 6 仕上げ | ショートカット一覧、控えの保存、.deb | APPLaunch から起動できる |

段階 1 で `zc-core` の型と各 crate の公開 API の雛形を先に決める。以降は API が
固まっているので、段階 2〜5 の crate は並行して作れる（統合は段階ごと）。

### 11.2 モデルの振り分け

前提: Fable が最も設計・推論が強く、Opus がそれに次ぎ、Sonnet は仕様が明確で
テストで正しさを確かめられる作業に向く。並行作業は crate ごとに別の worktree /
ブランチで行い、統合とレビュー、実機での確認はメインのセッションが受け持つ。

| 担当 | 受け持ち | 理由 |
|---|---|---|
| **Fable** | 段階 1 の土台（`zc-core` の型・全 crate の API 雛形・イベントループ・スレッド構成と受け渡し・版番号による取り消し・flush スレッドとフラッシュ計画）、`zc-ui` のエディタ表示（可変行高レイアウト）、`zc-markdown` のライブプレビュー | 後から変えにくい設計の中心。全体の性能と、カーソル位置と表示位置の対応が最も難しい |
| **Opus** | `zc-input`（ドライバのモディファイア仕様・grab・自前リピート）、`zc-font`（ラスタライズ・キャッシュ・色の表）、`zc-highlight` のエンジン（規則 → DFA のコンパイラ・埋め込み形式・文脈スタック・`.sublime-syntax` 変換ツール）、`zc-skk`、`zc-term`、§8 の書き込み層（原子的な保存・CRC 付き形式・2 段の控え） | 仕様が込み入っていて、細かい正しさが要るが、範囲ははっきりしている |
| **Sonnet** | `zc-display` の PNG 出力と render-test の仕組み、各言語の `language.toml` と見本（7 言語）、`zc-buffer`、`zc-intel` の最初の版（単語補完・構文チェックの実行・アウトライン）、ツリー・タブ・ステータスバー・ショートカット一覧、.deb と build.sh | API とテストが先に決まっていれば、仕様どおりに作れる |

後の版の LSP クライアント（`zc-intel` の差し替え、サーバの起動・停止の管理）は Opus。

- 各担当への指示は「この文書の該当節 + `zc-core` の型 + 受け入れテスト」で渡す
- 言語の追加は、仕組みができた後は Sonnet で十分（`languages/` にファイルを置き、
  見本のテストが通ることを確かめるだけ）
- 担当が API を変えたくなったら、勝手に変えず統合側（メインのセッション）に戻す
