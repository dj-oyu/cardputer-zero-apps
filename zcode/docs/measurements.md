# zcode 設計の根拠になる実測値

`design.md` の判断の元になった数字を、測り方と条件ごとにまとめる。数字を
書き換えるときは、ここを直してから design.md を合わせる。

**共通の条件**: CardputerZero 実機（Raspberry Pi Compute Module 0 Rev 1.0、
Raspberry Pi OS = Debian 13 aarch64、kernel 6.18.39+rpt-rpi-v8、microSD）。
デスクトップ（labwc）と APPLaunch（ランチャー表示中）が常駐した状態。
2026-11-16 計測。温度は 55〜59℃、スロットリング無し（`vcgencmd get_throttled` = 0x0）。
ベンチマークのコードは `../bench/`（使い方は `../bench/README.md`）。

表の「p50 / p95」は中央値と 95 パーセンタイル。

## 1. 液晶（fb0）

液晶は ST7789V（SPI0、spi-max-frequency 60MHz）、ドライバは panel-mipi-dbi-spi
（DRM の fbdev エミュレーション、`card1-SPI-1`）。stride 640 バイト、RGB565。

### 1.1 書き込みから SPI 転送開始まで

方法: SPI コントローラの送信バイト数
（`/sys/class/spi_master/spi0/statistics/bytes_tx`）を細かく読み、変化した時刻を見る。

| 条件 | 転送開始まで | 出典 |
|---|---|---|
| 書くだけ（fsync なし）・テキスト 1 行（11 画素行） | 中央値 30ms、最小 0.9ms、最大 56ms | `py/fb_spi_latency.py`、n=12 |
| 書くだけ・全画面 | 中央値 42ms、最大 62ms | 同上 |
| 書いて fsync・1 画素行 | p50 1.5ms / p95 5.2ms / 最大 6.4ms | `mcbench fb2`、n=12 |
| 書いて fsync・13 画素行（テキスト 1 行分） | p50 4.6ms / p95 6.5ms / 最大 6.9ms | 同上 |
| 書いて fsync・全画面 | p50 9.6ms / p95 12.2ms / 最大 12.4ms | 同上 |

- fsync しないと遅延 I/O の周期（約 50ms）を待つ。**fsync すると 25〜50ms 縮む**
- 転送開始までの待ちは、変えた行数にほぼ比例する（約 50µs/行）

→ design.md §2、§5.1（書いたら fsync）、§5.2（範囲を小さく保つ）、§6.1

### 1.2 fsync は呼び出し側を止めるか

| 条件 | 所要 | 出典 |
|---|---|---|
| fsync（直前に何も無いとき）・1 行 / 13 行 / 全画面 | p50 65µs / 73µs / 155µs | `mcbench fb`、n=25 |
| mmap への書き込み・1 行 / 13 行 / 全画面 | p50 34µs / 53µs / 304µs | 同上 |
| 直前の fsync の直後に次の fsync（直前が 1 行） | p50 0.7ms、最大 1.6ms | `mcbench fb2`、n=8 |
| 同（直前が 13 行） | p50 1.1ms、最大 2.3ms | 同上 |
| 同（直前が全画面） | p50 7.1ms（7.10〜7.19ms） | 同上 |
| 直前の fsync から 1ms 以上あけた場合 | 50〜80µs に戻る | 同上 |
| 全画面の転送中に別の行を mmap に書く | p95 12µs、最大 19µs（別スレッドが全画面 fsync を連発中でも最大 145µs） | `mcbench fb` |

- fsync は転送の完了を待たない（転送はカーネルのワーカーが別コアで行う）
- **続けて fsync すると止まる**。原因のカーネル内部は未特定

→ design.md §3（fsync はメインで呼ばない）、§4.2（flush スレッド）、§5.1

### 1.3 転送の量と時間

| 項目 | 値 | 出典 |
|---|---|---|
| 転送範囲 | 変更されたページを含む 1 つの行範囲（横は常に全幅）。1 ページ 4KB ≒ 6.4 行 | ドライバの挙動と SPI のバイト数 |
| 全画面の転送 | 65,532 + 43,268 バイトの 2 回。1 回目に 10.5ms → 実効約 50Mbit/s、**全体で約 17.4ms**（2 回目は実効速度からの計算値） | `mcbench fb2` |
| fsync から全画面の転送完了まで | p50 約 27ms | 同上 |
| 全画面の書き込み＋fsync を 12 回連続 | 9.9ms で戻り、SPI に出たのは 2 フレーム分（カーネルが最新の内容にまとめる） | `mcbench fb` |

→ design.md §1（スクロールの目標）、§5.3（スクロールのリピートは 20 回/秒）

## 8. キー入力（実機 2 号機、ランチャーの「zcode (dev)」から起動、2026-11-16）

方法: `zcode --keytest --stats` をランチャーから正式に起動し、ユーザーに決まった順で
押してもらった（`docs/stage1-notes.md` §6 の手順 2）。ログは `/tmp/zcode-keytest.jsonl`。

### 8.1 モディファイアの届き方

ドライバは Shift / Sym / Fn のどの押し方も「モディファイアのキーを押している間」と
して送る。アプリは押下〜離上で状態を持てばよく、特別な扱いは要らない。

| 押し方 | 届くイベント（Shift = KEY_LEFTSHIFT 42 の例。Sym = 383、Fn = 389 も同じ形） |
|---|---|
| 押しながら | 物理的に押したときに押下、離したときに離上 |
| 1 回タップ（ワンショット） | タップした時点で押下。**次のキーを離した直後**に離上（次の 1 打鍵だけに効く） |
| 2 回タップ（ロック） | 押下は 1 回だけ。**解除のタップまで押されたまま**。2 回目のタップは届かない |

- Sym+R は KEY_KP7（71）で届き、表どおり `-`。Fn+5 は KEY_F5、Fn ロック中の
  F / Z / X / C は ↑ / ← / ↓ / →（KEY_UP 103 / LEFT 105 / DOWN 108 / RIGHT 106）
- Ctrl+S、Alt+B、Ctrl+Shift+K は、モディファイアの押下 → キー → 離上の順で届く
- `SYN_DROPPED` は 0 回（速打ち 11 打鍵を含む 105 イベント。速打ちは打鍵の間隔 0.13〜0.3 秒で、
  11 回とも押下と離上がそろって届いた）

### 8.2 遅延（n = 105 イベント）

| 区間 | p50 | p95 | 最大 |
|---|---|---|---|
| カーネルのタイムスタンプ → zcode が `read()` | 59µs | 109µs | 462µs |
| カーネルのタイムスタンプ → そのフレームの `fsync(fb0)` を呼ぶまで | 1.4ms | 2.4ms | 7.3ms |

- これに fsync → 転送開始（13 行で p50 4.6ms、§1.1）と転送（約 1.3ms）を足すと、
  打鍵 → 液晶への転送完了は p50 で約 7ms。設計の目標（§1）の中
- キーを押してからカーネルがタイムスタンプを付けるまで（tca8418 の割り込みと I2C の
  読み取り）はソフトウェアでは測れない
- このときの起動 → 最初のフレームは 117.8ms（ランチャーから起動。ファイルが
  ページキャッシュに無い状態。SSH から続けて起動したときは 10〜12ms）。RSS 5.7MB

## 9. 起動（実機 2 号機、段階 2 の実行ファイル約 3.1MB、2026-11-17）

`--stats` の起動の区切り（`main` の始まりから。exec と動的リンクは含まない）と、区切りごとの
ページフォールト（メジャー = 記憶装置から読んだ回数）。

| 条件 | 最初のフレームまで | メジャーフォールト |
|---|---|---|
| ランチャーから（エディタ、`main.py`） | 8.8ms | 0 |
| SSH から、2 回目以降（エディタ） | 9.0〜10.2ms | 0 |
| SSH から、実行ファイル・フォント・キー配列をページキャッシュから追い出して（エディタ） | 33.8ms（フォントの読み込み 20ms） | — |
| 同じく追い出して、キー確認画面（段階 1 の実行ファイル / 段階 2） | 78.5ms / 78.8ms（初めての字の描画が 55ms） | — |

- 段階 1 と段階 2 で起動は変わらない（実行ファイルが 1.9MB → 3.1MB になった影響は見えない）
- ランチャーからの起動がときどき 100ms を超える（段階 1 で 117.8ms、段階 2 で 104.8ms。
  どちらもそのときの「キー配列を読み終えた」が 55ms 前後）。続けて起動すると再現しない。
  メモリが詰まっている（空き 36〜60MB、zram スワップ 170MB 使用）ときの最初の起動で、
  ページの回収かスワップの読み戻しを待っていると考えているが、まだ確かめていない
  （この版の `--stats` はメジャーフォールトを出すので、次に起きたらそれで見分ける）
- `/proc/pressure`（PSI）はこのカーネルでは使えない

## 10. 端末の解析（zc-term、2026-11-17）

`crates/zc-term/examples/termbench.rs`。pty を使わず、8KB ずつ `vte` に流し込んで画面
（53 桁 × 13 行、スクロールバック 1000 行）を更新する。各 4MB、3 回の最短。
「vte だけ」は字を数えるだけの `Perform` で、画面を更新しない分。

| 入力 | 開発コンテナ（x86_64、release） | 実機（2 号機、1GHz） | 実機・vte だけ |
|---|---|---|---|
| ascii（英数字の行、約 55 バイト/行） | 244MB/s（64KB で 0.27ms） | **8.6MB/s（64KB で 7.7ms）** | 136MB/s |
| mixed（SGR の 16 / 256 / truecolor、カーソル移動、行の消去） | 237MB/s | **9.4MB/s（7.0ms）** | 33MB/s |
| cjk（日本語が半分ほどの行） | 316MB/s | **12.1MB/s（5.4ms）** | 68MB/s |

- 時間の大半は画面の更新（1 字ごとのマスの書き込みと、1 行ごとのスクロール）で、`vte` の
  解析そのものは 1 割未満〜3 割。実機は x86_64 の 25〜30 倍遅い（順序どおりに実行する A53）
- 1 回の起床の上限 2ms（design.md §4.3）で読めるのは 16KB 前後。出力が流れ続けても
  メインは 2ms ごとに入力を見られる。描画を 30fps に間引けば CPU 1 つで追いつく速さ
- ASCII を行の途中に書く速い道を入れて 8.5 → 10.0MB/s（ascii）
- スクロールバックをマスの格子（1 マス 16 バイト、53 桁 1000 行で 0.85MB）のまま持つと
  ascii 10.0MB/s。字（4 バイト）と見た目の変わり目だけに詰めると約 0.3MB で 8.6MB/s。
  メモリを優先して詰める方にした。UTF-8 の文字列に詰めると 6.8MB/s まで落ちた

→ design.md §4.3・§9（読み取りと解釈はメインで、1 回の起床で 64KB か 2ms まで）

## 11. SKK 辞書（zc-skk、2026-11-17）

`crates/zc-skk/examples/skkbench.rs`（aarch64 の release ビルド）。実機（2 号機、1GHz）の
`/usr/share/skk/SKK-JISYO.L`（4,489,936 バイト、送りあり 15,995 項目・送りなし 159,791 項目）。
冷えた状態は `posix_fadvise(DONTNEED)` でページキャッシュから落として作る。2 回測って同じ傾向。
