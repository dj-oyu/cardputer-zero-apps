# zcode 設計の根拠になる実測値

`design.md` の判断の元になった数字を、測り方と条件ごとにまとめる。数字を
書き換えるときは、ここを直してから design.md を合わせる。

**共通の条件**: CardputerZero 実機（Raspberry Pi Compute Module 0 Rev 1.0、
Raspberry Pi OS = Debian 13 aarch64、kernel 6.18.39+rpt-rpi-v8、microSD）。
デスクトップ（labwc）と APPLaunch（ランチャー表示中）が常駐した状態。
2026-11-16 計測。温度は 55〜59℃、スロットリング無し（`vcgencmd get_throttled` = 0x0）。
ベンチマークのコードは `../bench/`（使い方は `../bench/README.md`）。

表の「p50 / p95」は中央値と 95 パーセンタイル。

## 1. 液晶（fb0）

液晶は ST7789V（SPI0、spi-max-frequency 60MHz）、ドライバは panel-mipi-dbi-spi
（DRM の fbdev エミュレーション、`card1-SPI-1`）。stride 640 バイト、RGB565。

### 1.1 書き込みから SPI 転送開始まで

方法: SPI コントローラの送信バイト数
（`/sys/class/spi_master/spi0/statistics/bytes_tx`）を細かく読み、変化した時刻を見る。

| 条件 | 転送開始まで | 出典 |
|---|---|---|
| 書くだけ（fsync なし）・テキスト 1 行（11 画素行） | 中央値 30ms、最小 0.9ms、最大 56ms | `py/fb_spi_latency.py`、n=12 |
| 書くだけ・全画面 | 中央値 42ms、最大 62ms | 同上 |
| 書いて fsync・1 画素行 | p50 1.5ms / p95 5.2ms / 最大 6.4ms | `mcbench fb2`、n=12 |
| 書いて fsync・13 画素行（テキスト 1 行分） | p50 4.6ms / p95 6.5ms / 最大 6.9ms | 同上 |
| 書いて fsync・全画面 | p50 9.6ms / p95 12.2ms / 最大 12.4ms | 同上 |

- fsync しないと遅延 I/O の周期（約 50ms）を待つ。**fsync すると 25〜50ms 縮む**
- 転送開始までの待ちは、変えた行数にほぼ比例する（約 50µs/行）

→ design.md §2、§5.1（書いたら fsync）、§5.2（範囲を小さく保つ）、§6.1

### 1.2 fsync は呼び出し側を止めるか

| 条件 | 所要 | 出典 |
|---|---|---|
| fsync（直前に何も無いとき）・1 行 / 13 行 / 全画面 | p50 65µs / 73µs / 155µs | `mcbench fb`、n=25 |
| mmap への書き込み・1 行 / 13 行 / 全画面 | p50 34µs / 53µs / 304µs | 同上 |
| 直前の fsync の直後に次の fsync（直前が 1 行） | p50 0.7ms、最大 1.6ms | `mcbench fb2`、n=8 |
| 同（直前が 13 行） | p50 1.1ms、最大 2.3ms | 同上 |
| 同（直前が全画面） | p50 7.1ms（7.10〜7.19ms） | 同上 |
| 直前の fsync から 1ms 以上あけた場合 | 50〜80µs に戻る | 同上 |
| 全画面の転送中に別の行を mmap に書く | p95 12µs、最大 19µs（別スレッドが全画面 fsync を連発中でも最大 145µs） | `mcbench fb` |

- fsync は転送の完了を待たない（転送はカーネルのワーカーが別コアで行う）
- **続けて fsync すると止まる**。原因のカーネル内部は未特定

→ design.md §3（fsync はメインで呼ばない）、§4.2（flush スレッド）、§5.1

### 1.3 転送の量と時間

| 項目 | 値 | 出典 |
|---|---|---|
| 転送範囲 | 変更されたページを含む 1 つの行範囲（横は常に全幅）。1 ページ 4KB ≒ 6.4 行 | ドライバの挙動と SPI のバイト数 |
| 全画面の転送 | 65,532 + 43,268 バイトの 2 回。1 回目に 10.5ms → 実効約 50Mbit/s、**全体で約 17.4ms**（2 回目は実効速度からの計算値） | `mcbench fb2` |
| fsync から全画面の転送完了まで | p50 約 27ms | 同上 |
| 全画面の書き込み＋fsync を 12 回連続 | 9.9ms で戻り、SPI に出たのは 2 フレーム分（カーネルが最新の内容にまとめる） | `mcbench fb` |

→ design.md §1（スクロールの目標）、§5.3（スクロールのリピートは 20 回/秒）

### 1.4 ほかのプロセスによる SPI の使用

| 状態 | SPI 送信量 | 出典 |
|---|---|---|
| APPLaunch がランチャー表示中（1 回目の計測） | 約 35〜39 万バイト/秒（全画面の約 3.2 回/秒）、APPLaunch の CPU 約 9% | sysfs の統計、`/proc/<pid>/stat` |
| 同（2 回目の計測） | 約 2.6 万バイト/秒 | `mcbench fb` |

- 画面の状態で変わる。**zcode の起動中に APPLaunch が再描画を止めるかは未確認**
  （止めないと zcode の画面が上書きされる。段階 1 で確認する）
- 液晶を使っているのは APPLaunch（と、そこから起動したアプリ）だけ。labwc は HDMI 側
  （`card0`）を使い、液晶には触らない
- SPI0 には spidev が 2 つ（`spi0.1`、`spi0.2`）もある。Cap を使うアプリと液晶が
  バスを取り合う可能性は未計測

## 2. CPU とクロック

| 項目 | 値 | 出典 |
|---|---|---|
| ガバナ | ondemand、600MHz〜1GHz | sysfs |
| 負荷がかかってから 1GHz に上がるまで | **3 回とも 100ms**（sampling_rate=100000） | `mcbench ramp` |
| 上がった後に保つ時間 | 1〜5 秒（sampling_down_factor=50） | `mcbench freq` |
| 100ms 間隔の軽い負荷（打鍵の間隔に相当） | ほぼ 600MHz のまま（全画面の合成 p50 395µs） | 同上 |
| 全画面の文字合成（13 行 × 53 字、色の表を引く方式） | 600MHz で 370µs、1GHz で 222µs | `mcbench freq` / `pool` |

→ design.md §2、§6.1（打鍵の処理は 600MHz で走る前提）

## 3. スレッド

### 3.1 受け渡し・生成・優先度

| 項目 | 値 | 出典 |
|---|---|---|
| eventfd で起こして poll で受ける（20ms 間隔＝打鍵に近い） | 起床まで p50 32 / p95 56µs、往復 p50 53 / p95 89µs | `mcbench handoff`、n=150 |
| 同（連続） | 起床まで p50 21 / p95 27µs、往復 p50 46 / p95 72µs | 同上、n=500 |
| 最大値 | 1.7ms が 1 回 | 同上 |
| コア固定 | 間隔ありでは差が出ない（28µs 対 32µs）。std の mpsc（futex）も同等 | 同上 |
| スレッド生成 | 1 本 130〜340µs、RSS +29KB/本 | `mcbench mem` |
| `RLIMIT_RTPRIO` / `RLIMIT_NICE` | 0 / 0（リアルタイム優先度も負の nice も使えない） | 同上 |
| sleep 5ms の超過 | p50 82µs、最大 181µs | `mcbench jitter` |
| timerfd 33ms ＋ poll の超過 | p50 38µs、最大 103µs | 同上 |

→ design.md §4.2（常駐ワーカー、コア固定しない、優先度は下げる方向だけ）

### 3.2 描画処理を並列化した場合（常駐プールで全画面 1 回分を n 分割、所要 p50）

| 処理 | n=1 連続 / 40ms 間隔 | n=2 | n=4 |
|---|---|---|---|
| 配るだけ（空の仕事） | 0 | 42 / 53µs | 60 / 61µs（p95 約 150µs） |
| 字形合成 13×53 字 | 220 / 257µs | 147 / 191µs | 100 / 149µs |
| 108KB コピー | 29 / 97µs | 46 / 137µs | 53 / 155µs |
| 行差分（全行同じ） | 106 / 174µs | 60 / 212µs | 57 / 227µs |
| memmove で 1 行スクロール（参考、n=1） | 43µs | — | — |

出典 `mcbench pool`。実行中にクロックが 600MHz と 1GHz の間で動いており、列ごとの
条件はそろっていない。それでも「打鍵の間隔では並列化で縮まない」傾向は一貫している。

### 3.3 n スレッドが独立に同じ仕事をしたときの合計スループット

| 処理 | 1 本 | 4 本での倍率 |
|---|---|---|
| DFA の表引き | 82〜94MB/s | 3.7〜4.1 倍 |
| 字形合成 | 4,440 画面/秒 | 2.3 倍（3 本で頭打ち） |
| memcpy 4MB | 896MB/s | **0.92 倍**（メモリ帯域は 1 コアで飽和） |

出典 `mcbench scale`。DFA と字形合成の倍率は、1 本のときの一部が 600MHz で走って
いるため、やや高めに出ている。

→ design.md §4.1（描画処理は並列化しない、マルチコアは待ちの回避に使う）

## 5. フォントと字形（swash）

| 対象 | 1 字 p50 | 備考 | 出典 |
|---|---|---|---|
| DejaVu Sans Mono 11px（ヒンティングあり）ASCII 94 字 | 26µs | 合計 2.7ms | `glyphbench` |
| Noto Sans CJK 12px 漢字 300 字（2 回目） | 66µs | 合計 20ms、キャッシュ 42KB（1 字約 140 バイト） | 同上 |
| 同（初回） | 84µs | **合計 302ms、p95 5.4ms、最大 16ms**（SD からのページイン） | 同上 |
| かな 83 字（初回） | 53µs | 最大 13ms | 同上 |
| 2 書体の FontRef を開く（初回） | 12.7ms | | 同上 |
| 初めて描く漢字 300 字を並列にラスタライズ | 1 本 24.2ms → 2 本 12.9ms → 4 本 11.6ms | | 同上 |

- 初回が遅いのは SD からのページインで、**1 回の待ちが 5〜16ms**
- `mincore` で常駐を確かめる方法は使えない（自分が持ち主でないファイルでは常に
  「常駐」と返る）

→ design.md §3（mmap にメインで触らない）、§5.4（assist スレッド、2ms だけ待つ、
キャッシュ 512KB）

## 6. ハイライト

| 方式 | 1 行あたり | 最初のハイライト | 読み込み・メモリ | 出典 |
|---|---|---|---|---|
| syntect 5（`default-fancy`、全 75 言語のダンプ） | **1.73〜1.91ms**（300 行で 518〜572ms） | **185〜209ms**（正規表現のコンパイル込み） | 読み込み 5.7〜5.9ms・+1.2MB、Python を使うと +11.5MB | `hlbench`、2 回実行 |
| 規則をビルド時に DFA 化（regex-automata 0.4、多パターン dense DFA、文脈 2 つ） | **0.0039〜0.0045ms**（300 行で 1.2〜1.3ms） | 止まらない | バイト列からの読み込み 2.4ms、メモリ増加ほぼ 0 | `dfabench` |
| DFA のコンパイル（ビルド時にやる分） | — | — | 460ms。Unicode の文字クラスを使うと Python の通常文脈だけで 1,257KB | 同上 |

- DFA では Unicode の単語境界（`\b`）を使えない（ASCII の単語境界にする）
- 全言語ダンプの圧縮後サイズは 333KB

→ design.md §7（独自の規則をビルド時に DFA 化、Unicode 文字クラスを使わない）
