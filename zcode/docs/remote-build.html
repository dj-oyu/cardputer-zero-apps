外でビルド・試験・型検査する仕組み

zcode の設計（2026-11-16。Fable のレビューを反映）。まだ何も実装していない。実機は CardputerZero（CM0: Cortex-A53 ×4・RAM 352MB・SD カード）。 各項目の ▸ を開くと、理由や詳しい説明が出る。レビュー はレビューで足した・変えたところ。

実行は実機で

書くプログラムは液晶・キー・カメラ・Bluetooth など実機にしか無いものに触る。外で動かしても意味が無い。

重い仕事は外のビルド係に

Rust のビルドと型検査、npm の依存があるプロジェクト、試験。ビルド係は Cloudflare Containers か PC の開発コンテナ（同じ中身）。

実機側は小さな別プロセス レビュー

zc-remote: 必要なときだけ起動し、使わなければ終わる。速さを決めるのは暗号の CPU ではなく、往復の回数・運ぶバイト数・メインと SD に触らないこと。

決めたこと（2026-11-16 ユーザーが決定）

① TLS の暗号の実装 決定

ring（2026-11-16 ユーザーが決定）。C とアセンブリを含むが、クロスの gcc だけで作れ、監査と利用実績がある。「pure Rust だけ」の方針の例外は zc-remote に限る（zcode 本体は pure Rust のまま）。pure Rust の rustls-rustcrypto（試験的・未監査）は採らない。§6

② 再起動後のオフライン 決定

最後に成功した実行ファイルを 1 つだけ SD に残す（2026-11-16 ユーザーが決定）。「再計算できるキャッシュは SD に書かない」の例外（ネットが無いと作り直せないため）。書く時機は控えの段 2 と同じ。§6.5

③ Cloudflare は前提か 決定

前提（2026-11-16 ユーザーが決定）。レビューの異論（永続ディスクのある VM を tailnet に入れる案）は採らない。キャッシュはスナップショットと sccache で解く。§10

却下した「どこでやるか」

実機で cargo を使う 却下

実機のメモリ・SD・時間のどれも足りない。

理由を詳しく
  • メモリ: rustc は依存のある crate を 1 つビルドするだけで数百 MB 使うことがよくある。実機で OS から見えるのは 352MB で、空きは 80〜110MB。スワップ（zram）に追い出されて極端に遅くなるか、メモリ不足で殺される
  • SD への書き込み: target/ は数百 MB〜GB 単位になり、ビルドのたびに書き換わる
  • 置き場: Rust のツールチェーンそのものが 1GB 前後
  • 時間: A53（最大 1GHz）で依存込みのビルドは数分〜十数分の見込み
  • cargo check も依存のメタデータをビルドするので同じ。rust-analyzer は論外

数字は見込み。実機では測っていない。

実機に npm を入れる 却下

依存解決が重く、SD に小さなファイルを大量に書き、インストールスクリプトが実機で動く。

理由を詳しく
  • メモリ: npm 自体が Node（V8）のプログラム。依存の木の解決に数十〜数百 MB 使う
  • SD: 1 回のインストールで数千〜数万の小さなファイルを、キャッシュと node_modules の二重に書く。ext4 では 1 ファイルごとにメタデータとジャーナルも書かれ、SD は大きな消去単位で書き直すので、小さな書き込みは増幅される。途中で電池が切れると node_modules が半端に残る
  • サプライチェーン: postinstall などが実機の jimmy の権限で動き、ファイルや SSH の鍵に届く
  • LLRT も「1 ファイルにまとめて」と言っているので、どのみちまとめる手順が要る

実行もビルド係でする 却下

試験以外は実機で実行する。

理由を詳しく
  • 実機にしか無いもの: 液晶（fb0）・キー・カメラ・Bluetooth・GPIO は、ビルド係には無い
  • 環境の違い: ビルド係は x86_64。aarch64 の実行ファイルを動かすには qemu が要り、OS・ライブラリ・/dev も違う
  • 対話と停止: 入出力と Ctrl+C をネット越しに中継することになる
  • 費用: Containers は動いている間ずっと課金。常駐するプログラムを試すと読めなくなる
  • 例外: ハードウェアに触らない試験はビルド係で動かして結果だけ返す

Workers だけでやる 却下

Workers（V8 の上の JS）では任意の実行ファイルを動かせない。受付の役にだけ使う。

理由を詳しく
  • cargo・gcc・npm 本体・TS 7 の tsc（Go 製）はどれも実行ファイルなので、Workers では動かない
  • esbuild の wasm 版と npm レジストリからの取得なら JS で書けるが、1 回あたりの CPU 時間とスクリプトの大きさに上限がある

2全体の形

3認証: 実機を誰だと認めるか

Cloudflare のビルド係はインターネットにいるので、「この依頼は自分の CardputerZero から来た」と確かめる必要がある。候補は 5 つ。

Access のサービストークン 採用

実機ごとに ID と秘密の組を発行し、つなぐときのヘッダに付ける（CF-Access-Client-Id / CF-Access-Client-Secret）。Access が門番になり、合わなければ Worker まで届かない。

持ち方と、失くしたとき
  • 実機では ~/.config/zcode/remote-token.json（権限 0600。広ければ読まない）。{"scheme":"cf-access-service-token", ...} の形で方式を書いておく。リポジトリには入れない。ログにも出さない
  • 有効期限は 1 年程度。期限の 1 週間前に通知、更新は 1 年ずつ。秘密のローテーションは古い秘密を 1 時間〜30 日まで並行して使える
  • 機体ごとに別のトークン（タグに機体名）。失くしたらそのトークンだけ無効にする
  • Worker は Access が付ける JWT を Web Crypto（RS256・ES256・Ed25519）で確かめる。Worker に秘密は置かない
  • 確かめるのはつなぐとき（WebSocket の Upgrade）だけ。長い接続の途中でトークンの期限が来ても切らない
  • F5 で動かすプログラムも jimmy なのでトークンを読める。守りはサーバ側に置く: 回数制限・1 日のジョブ数・同時に動かすコンテナ数の上限。漏れても「ビルド時間を使われる」だけにする

Tailscale のノード ID トークン 将来

実機が tailscale id-token <宛先> で Tailscale に署名された短命のトークンをもらい、Worker が Tailscale の公開鍵で確かめる。秘密を実機に置かずに済む、いちばん良い形。

今は使えない理由と、乗り換えを安くする作り
  1. コマンドはある（実機の Tailscale 1.104.7）が「作業中」の扱いで、TAILSCALE_USE_WIP_CODE=1 を付けないと動かない
  2. 付けて試すと、Tailscale のサーバーが "id-token access denied" と断った（2026-11-16）。公式の文書に有効にする手順が無い
  3. 資料にあった「Workload Identity Federation」は向きが逆。GitHub Actions などが出したトークンを Tailscale が受け取るためのもので、Tailscale のノードが外向けのトークンを出す話ではない

レビュー 乗り換えを安くするため、zc-remote の中で認証を 1 つの口にまとめる:

trait Credential {
    fn headers(&mut self, out: &mut Vec<(HeaderName, String)>) -> Result<(), AuthError>;
    fn rejected(&mut self) -> Retry;   // 401 / 403 / 302 を受けたとき
}
// 実装: None（PC・tailnet）、AccessServiceToken、将来の TailscaleIdToken { audience }
  • Worker で身元を 1 つの形（device_id）に直してから DO に渡す。DO と受付のプログラムは方式を知らない。移行中は 2 方式を並行して受ける
  • ID トークンは取るのに数十〜100ms かかる見込みなので、期限の 60 秒前まで RAM に持つ
  • PC の経路なら、受付のプログラムが tailscaled に「相手はどのノードか」（whois）を聞ける。ノードの身元は PC の経路なら今日から使える

Tailscale（tsidp）を Access の OIDC ログインにする 却下

OIDC は「人がブラウザでログインする」ための仕組みで、画面の無いプログラムが毎回の依頼で使う形になっていない。下で順を追って説明する。

なぜ OIDC が合わないのか（図つき）

OIDC の流れ（認可コードフロー）。Access のログインに外部の IdP（ここでは tsidp）を使うと、こう動く:

  1. A: ブラウザと人が前提。③ でログイン画面を出し、④⑤ で画面を移って戻る。zcode が F5 や保存のたびに出す依頼は、画面の無いプログラムの通信なので、この流れを踏めない。Access の OIDC 連携の文書も、ブラウザが移る先の URL（callback）を登録して、ダッシュボードの「Test」ボタンで試す、という人向けの手順しか書いていない
  2. B: tsidp に「内」と「外」の両方から届く必要がある（文書と仕組みからの推測で、試してはいない）。
    • ③ で tsidp は「どの tailnet の接続から来たか」で人を見分けるので、ブラウザは tailnet の中から tsidp に届く必要がある
    • ⑥ は Cloudflare のサーバーが直接 tsidp に問い合わせる。Cloudflare は tailnet の中にいないので、tsidp のトークンと公開鍵の窓口を Funnel などでインターネットに出す必要がある
    • 自分の IdP をインターネットに公開することになる。tsidp の文書は tailnet の中で使う前提で、公開の話は無い。しかも tsidp は「実験的・互換性が壊れることがある」と書かれている
  3. C: 決まるのは「人」で、「機体」ではない。⑦ で手に入るのはログインした人のセッション。一定時間で切れるので、切れるたびに人がログインし直す必要がある。zcode が無人で依頼を出し続ける用途に合わない。失くした実機だけ止めたい、という要求にもサービストークン（機体ごとに 1 つ）の方が素直
抜け道もある: cloudflared access login <URL> を実機で動かすと、ログイン用の URL が出る。それを手元のスマホのブラウザで開いてログインすると、実機の cloudflared がトークンを受け取れる。画面の無い機械でも OIDC を通せるが、cloudflared を実機に入れる必要があり、セッションが切れるたびに人の手が要る。F5 を押したら「ログインし直して」と止まる作りになるので、採らない。
OIDC が向いている場面: 人がブラウザで見る画面（ビルドの履歴・試験の結果を見るダッシュボードなど）を作るなら、Access のログインに Tailscale の身元を使う形は自然。そのときにもう一度考える。

Tailscale の OAuth クライアントで確かめる 却下

Worker が Tailscale の API に「この機体は tailnet にいるか」を聞く形。証明にならない。

理由を詳しく
  • Worker が API で分かるのは「その名前の機体が tailnet にいる」ことまで。今の依頼が本当にその機体から来たかは分からない。名前を名乗るだけなら誰でもできる
  • デバイス一覧を読む権限（devices:core）は機体の承認・削除・タグの変更もできる強い権限で、その秘密を Worker に置くことになる
  • API トークンは 1 時間で切れるので、Worker が取り直し続ける必要もある

Cloudflare Tunnel で tailnet とつなぐ 却下

PC をビルド係にする場合の通り道の候補。実機と PC はすでに Tailscale でつながっているので要らない。

理由を詳しく
  • Tunnel のプライベートネットワークは、Cloudflare の端末アプリを入れて組織に登録した利用者が、社内のネットワークに入るためのもの
  • 文書に「cloudflared は利用者側から始まった通信だけを中継する」とある。Worker やコンテナから tailnet の中の PC へ向かう通信に使えるかは書かれていない
  • 実機 → PC は Tailscale でそのまま届くので、Cloudflare を挟む利点が無い

4ビルド係（Cloudflare Containers）

イメージ

開発コンテナ（container/Dockerfile）がもと。Containers は linux/amd64 で作る前提で、開発コンテナも x86_64 で動いて aarch64 にクロスビルドするので合う。足すのは Node・npm・esbuild・TS 7 の tsc・受付のプログラム。

振り分けと寿命

DO がジョブの持ち主。使わなくなって 10〜30 分で止める。止めるときは SIGTERM、最大 15 分後に SIGKILL。冷えた状態からの起動は公式の目安で 1〜3 秒だが、レビュー Rust・クロス・Node 入りの GB 級のイメージで成り立つかは未確認。

大きさ

standard-2（1 vCPU・6GiB）だと、依存込みの Rust の初回ビルドは分単位の見込み。冷えるたびに起きるので、standard-4（4 vCPU・12GiB）とキャッシュを最初から組みにする。

キャッシュ（いちばんの課題）

ディスクは使い捨て。止まると cargo の target/・crate のキャッシュ・npm のキャッシュが全部消える。レビュー スナップショットか sccache は「次に試す」ではなく最初から計画に入れる。

手内容使いどころ
温めておく止めるまでの時間を長めに続けて作業している間は効く。ただしメモリの料金がずっとかかる（§9）
スナップショット依存をそろえた状態を写しておき、冷えたらそこから始める。durable_object 方式で使え、30 日保持、公開ベータの間は無料初回のビルドの重さを消す本命
R2 を FUSE でつなぐ公式に例がある。「SSD ほど速くない」ダウンロードしたものの置き場向き
sccache（置き場を R2）rustc の出力を crate ごとに R2 へRust の依存のビルドを使い回す
DO の名前の付け方と、2 台の機体 レビュー
  • 機体が 2 台ある。DO の名前を「プロジェクト」だけにすると、2 台の同じプロジェクトが同じコンテナに当たる。キャッシュの共有には良いが、作業フォルダを取り合う
  • どちらかにする: DO の中でジョブを直列にする、またはジョブごとに作業の木を分ける（キャッシュは共有）
  • 試験を x86_64 で動かすと、aarch64 用とホスト用で target/ が 2 つになり、キャッシュもビルド時間も倍になる。承知の上で採る
安全面
  • build.rs・postinstall などの任意のコードと試験は、このコンテナの中だけで動く。実機にも PC にも届かない。コンテナには秘密を入れない
  • 出来上がった実行ファイルは、結局実機で jimmy の権限で動く。ビルドを外に出しても、実行するコードそのものの安全性は変わらない

5送る形・返す形 レビューで変更

zc-remote とビルド係の中の受付のプログラムの約束。Cloudflare でも PC でも同じ。WebSocket 1 本に全部流す（制御は JSON、ファイルと実行ファイルはバイナリのフレーム。base64 にしない。64〜256KB に刻む）。全メッセージにジョブ id、最初の hello に約束の版。

5.1 送り方: 目録 → 足りない分だけ

なぜ tar をやめるのか（mtime の罠） レビュー
  • 正しさの問題: CM0 には時計の電池（RTC）が無く、NTP が合うまで時計がずれる。cargo はファイルの更新時刻（mtime）で変更を判定する
    • tar で実機の mtime を持ち込み、時計が進んでいれば → 毎回全部ビルドし直し
    • 時計が遅れていれば → 変更が拾われず、古いビルドが黙って返る
    • mtime を捨てて毎回全部書き直せば → 毎回全部ビルドし直し
    なので受付側は必ず「中身のハッシュが変わったファイルだけ書く」。それなら最初から目録で送る
  • コンテナが冷えても、木を DO か R2 に持っていれば実機は送り直さない。切れた後の再送も足りない分だけ
  • 手打ちのプロジェクトは数十 KB なので、転送量の差は小さい。採る理由は正しさと、やり直しの強さ
変わったファイルの見つけ方・ハッシュ
  • zc-remote は RAM に {パス → (大きさ, mtime_ns, inode, sha256)} を持つ。依頼のたびに stat で木を歩き（数百ファイルで数 ms の見込み）、食い違ったものだけ読み直す。SD には何も書かない
  • 「エディタが保存したファイル」だけに頼らない。ターミナルの git pull や scp でも変わる。走査の直前 2 秒以内の mtime のものは無条件に読み直す
  • ハッシュは SHA-256 だけ。実機の CPU には SHA の命令が無い（/proc/cpuinfo の Features は fp asimd evtstrm crc32 cpuid、実測）ので 30〜60MB/s の見込みだが、ソースの量なら問題にならない。TLS・Web Crypto・R2 もどのみち SHA-256。BLAKE3 は速いが NEON 版は C で、サーバ側に無い
  • 再起動後の初回は全部ハッシュし直す（1MB で 20〜30ms の見込み）
決める必要があるもの（プロジェクトの範囲・lock）
  • プロジェクトの根: [workspace] のある Cargo.toml までさかのぼるか
  • 根の外への path = "../x" の扱い
  • 除外: target・node_modules・.git と .gitignore。シンボリックリンクはたどらない。上限は「1 ファイルの上限 + 1 回の合計の上限」
  • Cargo.lock が無いとき、ビルド係が作った lock を実機へ返して書く（無いと鍵が安定しない）。SD への書き込みは変わったときだけ、zc-store の原子的な保存で

5.2 ジョブの種類

kind中でやること返すもの
buildRust: F5 用のプロファイル（§5.4）で --target aarch64-unknown-linux-gnu ／ C: aarch64-linux-gnu-gcc -mcpu=cortex-a53 ／ JS・TS: npm ci --ignore-scripts → tsc → esbuild実行ファイル（または 1 ファイルの JS）、診断
checkRust: cargo check --message-format=json ／ TS（npm の依存あり）: tsc --noEmit診断だけ
testcargo test ／ npm test（x86_64 のまま）試験の結果、診断

レビュー 以前の案の deps（依存の .d.ts 一式を実機に返す）はやめた。型定義は数千ファイル・数十 MB になりうり、SD に置けば npm を却下した理由と同じ、tmpfs に置けば RAM を食う。--lib es2022,dom だけで 91MB（実測）なので、依存の型まで読ませれば空きメモリを超える見込み。

5.3 ジョブは接続から切り離す

  • ジョブの持ち主は DO。接続が切れても続ける。実機はつなぎ直して attach {job, log_offset, artifact_offset} で続きを受ける
  • ジョブ id は「tree id + kind + オプション」のハッシュ。出し直しが自然に同じジョブに当たり、同じ鍵の結果があればビルドせずに返す
  • 取り消し: 新しい保存の check は、同じ接続で cancel を送ってから新しい job。受付側は cargo をプロセスグループごと止める。編集しただけ（保存なし）では取り消さない。F5 のビルドは次の F5 でだけ取り消す
  • 受付側は遅い相手を待たない。ログは受付側に全部残し、実機へはまとめて送る（§6.4）

// このあと同じ接続に、実行ファイルを zstd で圧縮したバイナリのフレーム
  • F5 は --release 固定にしない。待ち時間はビルドの時間と実行ファイルの大きさで決まる。F5 用は opt-level=2・LTO なし・incremental・debug=0・strip。配布用は別のオプションで
  • 返す前に strip し、zstd を高い圧縮率で（x86 側の仕事）。窓は 2MB 以下（実機の展開メモリを抑える）
  • 診断の行・桁は 0 始まり、桁は行の中の UTF-8 のバイト位置（zcode の Span と同じ）。rustc の JSON の桁は 1 始まりの文字数なので、受付のプログラムが直す。日本語のコメントでずれないように
  • 依存 crate やマクロ展開の先を指す診断は、手元の呼び出し元の位置に寄せる。寄せられなければ位置なしにしてステータスバーにだけ出す

6実機側のクライアント（性能） レビュー

速さを決めるのは暗号の CPU ではない。TLS のハンドシェイクの CPU は 600MHz でも 10〜30ms の見込みで、Wi-Fi の往復 2 回（40〜200ms）より小さい。効くのは 往復の回数・運ぶバイト数（とくに実行ファイル）・メインスレッドと SD に触らないこと。iPhone の Bluetooth テザリング（0.5〜1.5Mbit/s の見込み）では 3.2MB の実行ファイルの受信に 20〜50 秒かかり、ここが最大の時間になる。

6.2 通信と TLS

実機の CPU（実測）: fp asimd evtstrm crc32 cpuid — AES・SHA・PMULL の命令が無い。ondemand ガバナは短い処理では上がりきらないので、ハンドシェイクのような 10ms 級の処理は 600MHz 前提で見積もる。

処理（見込み）ring（アセンブリ）— 採用pure Rust（RustCrypto）— 不採用
X255190.3〜1ms0.5〜1.5ms
ECDSA P-256 検証（証明書の鎖で 2〜3 回）1〜2ms / 回3〜8ms / 回
TLS 1.3 のハンドシェイク全体の CPU5〜10ms15〜30ms

ChaCha20-Poly130560〜120MB/s30〜60MB/s

Wi-Fi の実効は良くて 1〜3MB/s、テザリングは 0.1MB/s 級なので、どの暗号でも回線より速い。冷えた接続は DNS + TCP + TLS + Upgrade で往復 3〜4 回（往復 20〜50ms なら 100〜250ms）。温まっていれば 0。

使うもの

  • rustls + 自前の小さな HTTP/1.1 Upgrade と WebSocket の枠組み。rustls の read_tls / write_tls を自分の poll() ループに載せる
  • 暗号の実装は ring（決定 ①）。C とアセンブリはクロスの gcc で作る。実機の CPU で使えない命令が入らないか、出来上がりを objdump で確かめる（runtimes/llrt/ と同じ確かめ方）
  • TLS 1.3 のみ、鍵交換は X25519 のみ、暗号は ChaCha20-Poly1305 だけを出す（サーバに AES-GCM を選ばせない。AES のコードも入らない）
  • ALPN は http/1.1 だけ。permessage-deflate は交渉しない（圧縮は自前）
  • 根の証明書は webpki-roots（埋め込み）。/etc/ssl/certs を SD から読まない
  • 実行ファイルの展開は pure Rust の ruzstd
  • PC の経路は TLS なし（tailnet の中は WireGuard で暗号化済み）。ssh を通り道にする案は暗号が二重になるのでやめ、ACL にポートを 1 つ足す

使わないもの

  • tokio・hyper・reqwest（実行ファイルが数 MB 増え、ランタイムのスレッドが増える）
  • aws-lc-rs（rustls の既定。大きくビルドが重い）
  • native-tls / openssl（aarch64 の libssl-dev が要る）
  • graviola（aarch64 で AES・SHA・PMULL を要求すると理解している。要確認。そうならこの CPU では動かない）
  • h2・HTTP/3（1 本の WebSocket では多重化の利点が無い）
  • 0-RTT（1 往復のために再送攻撃の扱いが増える）
接続を温める・時間切れ・時計
  • 温める方が再開より効く: Rust のプロジェクトを開いたとき、または最初の保存で、先につないでコンテナも起こす。TLS の再開チケットは RAM にだけ持つ（減るのは CPU 数 ms と証明書の数 KB で、往復は減らない）
  • 温める時間は 60〜90 秒。Cloudflare は無通信の WebSocket を 100 秒前後で切る（要確認）。待機中に ping は打たない（無線を起こし続ける）。静かに閉じ、次は再開でつなぐ
  • 時間切れ: DNS 2 秒、接続 3 秒、ハンドシェイク 5 秒。前回つながった IP を RAM に覚えて先に試す。IPv4 と IPv6 は少しずらして並行に（テザリングで IPv6 が通らない場合がある）
  • つなぐ前に分かることは待たない: /sys/class/net/<if>/operstate と既定の経路を見て、無ければ即「オフライン」
  • ジョブ中に 30〜45 秒何も届かなければ切れたとみなし、つなぎ直して attach。受付側は 15 秒黙ったら ping
  • やり直し: F5 は 0.5 秒から倍々で 3 回まで。保存時の check はやり直さない（次の保存が代わり）
  • Access の方針が Service Auth でないとログイン画面へ 302 が返る。302 と HTML は認証の失敗として扱い、たどらない
  • 時計: RTC が無いので、NTP の同期前は証明書の検証が「まだ有効でない」で落ちうる。その種類のエラーを見分け、/run/systemd/timesync/synchronized の有無を見て「時計が合っていない」と出す（実機にこのファイルがあるのは確認済み）

6.4 ログをターミナルパネルへ（打鍵を遅らせない）

  • 打鍵の邪魔になるのは CPU ではなく、メインの起床の回数と、パネルの行の SPI 転送（1 行で約 12.9KB、続けて fsync すると最大 7ms 止まる）
  • 受付側: ログは 50〜100ms か 4KB ごとにまとめて送る。全体に上限（たとえば 1MB）、超えたら末尾だけ + 「省略」の印
  • zcode 側: 専用スレッドは 1 行ごとに送らず、上限つきのバッファに足して、メインを起こすのは最短 33ms に 1 回（design.md §4.3 のターミナルの間引きと同じ）。直近 100ms 以内に打鍵があれば、ログの描画は次へ送る。あふれたら古い方を捨てる
  • いちばん簡単な形: F5 は「ターミナルパネルの pty で zc-remote build && 実行」。ログ・間引き・Ctrl+C がターミナルの仕組みで済み、診断だけ serve 経由で zcode に届ける。段階 3 のターミナルと合わせて決める

6.5 オフライン・電池

  • 電池: 暗号の CPU は 1 回の往復で数十 ms なので効かない。効くのは無線を起こす回数。待機中は ping を打たない。保存時の check は設定で「常に / 接続が温かいときだけ / 手動」
  • 再起動後のオフライン（決定 ②）: tmpfs は消えるので、最後に成功した実行ファイルを圧縮して ~/.cache/zcode/bin/ に プロジェクトごとに 1 つだけ残す。書くのは控えの段 2 と同じ時機（60 秒操作が止まったとき・電池が少ないとき・終了時）で、中身が変わったときだけ。書き方は zc-store の原子的な保存（一時ファイル → fsync → rename）。ネットが無いときの F5 は「前の版を実行する？」と聞き、RAM に無ければここから戻す

7.2 リモートの仕事は batch に載せない レビュー

rt.rs の Worker は依頼を 1 本で直列に実行する。batch はファイルを開く・ハイライトの残り・検索も受け持つので、数秒〜数分かかるリモートの check / build を載せると、その間ファイルが開けなくなる。zc-remote の相手をする専用スレッドを使う。今の保存時チェック（editor.rs の run_check、CancelToken::never()）も同じ問題を持っている（0.4 秒なので目立たないだけ）。

7.3 診断の型と、届くまでの編集 レビュー

// zc-intel（crate をまたぐなら zc-core）
pub struct Diagnostic {            // 今のまま + 任意の項目
    pub line: u32, pub col: Option<u32>,
    pub end: Option<(u32, u32)>,   // 範囲の終わり（あれば）
    pub severity: Severity, pub code: Option<Box<str>>,  // "E0308"
    pub message: String,
}
pub struct FileDiagnostics { pub path: Arc<Path>, pub diags: Vec<Diagnostic> }  // プロジェクト相対・'/' 区切り
pub enum DiagSource { Syntax, Remote }
pub struct DiagnosticSet {
    pub source: DiagSource,
    pub base: Version,             // 依頼したときの版
    pub complete: bool,            // 取り消し・失敗の結果では false
    pub files: Vec<FileDiagnostics>,
}
  • Diagnostic に file を 1 件ずつ足す形はやめる（確保が増え、タブ単位で動いている shift_diagnostics・marks_of・t.diags を全部直すことになる）
  • 置き換えは source ごと。今は t.diags = diags で丸ごと差し替えていて、実機の構文チェックとリモートの check が互いを消してしまう
  • complete のときだけ「今回出てこなかったファイルの診断」を消す。途中で切れた結果で波線を消さない
  • 開いていないファイルの分はプロジェクト側に持ち、開いたときに付ける（ツリーの赤い印・問題一覧にも使える）
  • 版: 今の AppEvent::Checked には版が無く、届いた診断がその時点のバッファにそのまま付く。リモートは数秒かかるので、その間に行を足すと波線がずれる。依頼時の Version を持たせ、タブ側はその版以降の行の変化を小さな記録（上限つき）に残して、届いた診断をずらしてから付ける。記録があふれたら桁を捨てる
  • 診断は 1 件ずつ AppEvent にせず、done でまとめて 1 回

9費用（Cloudflare Containers）

含まれる分（月 $5）

CPU 375 vCPU 分・メモリ 25 GiB 時間・ディスク 200 GB 時間。外への通信は北米・欧州で 1TB、それ以外で 500GB。

超過分

1 回のビルド

レビュー 温めておく間のメモリが本当の費用。メモリは CPU と違い、動いている間ずっと割り当てた分にかかる。standard-4（12GiB）は 1 時間 0.108 ドルで、含まれる 25GiB 時間は約 2 時間分。30 分温めると 1 回で含まれる分の 24% を使う。1 日 2 時間 × 30 日なら月 6 ドル強の超過の見込み。金額は小さいが、温める時間は短めにし、スナップショットで冷えた起動を速くする方を主にする。

10レビューの異論: Containers でなく常設の VM 採らない

2026-11-16 ユーザーが決定: Cloudflare が前提。この案は採らない。記録として残す。

いちばんの課題（使い捨てのディスクとキャッシュ）は Containers を選んだことから来ている。永続ディスク付きで、止めておける VM を tailnet に入れる形なら:

  • キャッシュの問題が消える（target/ もレジストリも残る）
  • 認証は tailnet（ACL と whois）で済み、サービストークンが要らない
  • 実機に TLS が要らない（PC の経路と同じ 1 本になる。決定 ① も消える）

代わりに、VM の起動・停止の管理と、止まっている間のディスクの料金がかかる。Cloudflare が前提なので採らない（決定 ③）。
