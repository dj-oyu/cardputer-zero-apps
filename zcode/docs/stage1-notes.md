## 2. API の決定と理由

### zc-core

| 型 | 決めたこと | 理由 |
|---|---|---|
| `Rect` / `RowRange` | 座標は `i16`、大きさは `u16`。行範囲は半開区間 | 画面の外にはみ出す矩形を許し、描画側で切り取る。転送の単位が行なので、変更は行範囲で表す |
| `Color` | RGB565 の `u16` そのもの。`Color::hex(0xRRGGBB)` は `const fn` | fb0 にそのまま書ける。配色は `palette`（モックの CSS 変数と同じ値） |
| `BlendLut` | 文字色と背景色から作る 16 色の表 | §5.4。濃度の上位 4bit で引くだけ |
| `Style` | `fg` + `bg: Option<Color>` + `Attrs` | 合成に背景色が要るので、`None` は「部品の地の色」。ハイライトは `fg` だけ決めればよい |
| `Canvas` | `u16` の配列。大きさは可変（既定 320×170）。変更の追跡はしない | 「どこを描き変えたか」は部品が `Damage` で返す（§3）。`blit_mask` が色の表で合成、`scroll_rows` が memmove |
| `Damage` | 優先度つきの行範囲を最大 6 個、ヒープなしで持つ | 部品が毎フレーム返す値なので軽くする。あふれたら近い 2 つをまとめる |
| `Priority` | `Cursor` < `Edit` < `Normal` < `Status` | §5.2 の優先順そのまま |
| `KeyEvent` | `key` / `mods` / `text` に加えて `repeat: bool` | リピートで作った打鍵を見分ける（保存などリピートさせない操作に渡さない） |
| `Key` | `Char(char)` は Shift なしの文字。レイヤーは持たない | レイヤーはドライバが解決して別のキーコードで届く |
| `Mods` | `SHIFT` / `CTRL` / `ALT` のほかに `SYM` / `FN`（参考情報） | 割り当ての照合は `chord()`（SHIFT / CTRL / ALT）だけ。SYM / FN は表示用 |
| `KeyChord` | `"Ctrl+Shift+K"` を読み書きできる | キー割り当て表とショートカット一覧の両方で使う |
| `Command` / `Motion` | モックの「ショートカット一覧の全項目」を列挙。`#[non_exhaustive]` | 表は `zcode/src/commands.rs` の 1 つ（§3） |
| `text::{Pos, LineRange, LineChange, LineSource, TokenKind, Span, Theme}` | テキストまわりの共通の型を `zc-core` に置いた | 横同士の依存を禁じている（§3）ので、`zc-buffer`・`zc-highlight`・`zc-intel`・`zc-markdown` がやり取りする型の置き場が要る |
| `version::{VersionCounter, CancelToken, Versioned, DocId}` | 依頼に `token()` を付け、ワーカーは `check()?`、メインは `take_if_current()` | §4.2「古い結果の扱い」を、どの crate も同じ書き方でできるようにする |
| `rt::{Notifier, main_channel, Worker, TimerFd, poll_fds}` | スレッドの受け渡しの部品を `zc-core` に置いた | `zc-font`（assist）や `zc-skk` が、`zcode` に依存せずにワーカーを使える |

`Worker` は「クロージャを順に実行する常駐スレッド 1 本」。結果はクロージャに持たせた
`MainSender<T>`（mpsc + eventfd）で返す。`submit_keyed` は、同じ鍵の実行待ちの依頼を
置き換える（storage の「同じファイルは最新だけ」）。`Drop` は溜まった依頼を実行して
から終わる（保存を書き切る）。依頼の中の panic はワーカーが受け止めて、次の依頼を続ける。

### zc-display

- `Display::present(&canvas, &damage)`: `damage` の行だけを提示用バッファと比べ、
  変わった行をコピーして flush スレッドを起こす。**`damage` に入っていない行は比べない**
  （部品の申告は広めでよい。中身が同じ行は差分で落ちる）
- 送り待ちの行は「行ごとの表」（1 行 1 バイト = 優先度）で持つ。flush が忙しい間に
  同じ行を書き換えても、表の上で自然に併合される（§5.1 の 4）
- flush スレッドは、間が 20 行未満の変更を 1 つのまとまりにし、優先度の高いまとまり
  から 1 つずつ「mmap に書く → fsync」する（§5.2）
- `FlushRecord`（fsync ごとの時刻）を `take_flush_log` と `set_flush_listener` で
  取り出せる。キー確認モードの「そのフレームの fsync の時刻」と計測に使う
- `FbBackend` は開いた時点の画面を控え、`Drop` で書き戻す。`emergency_restore()` は
  シグナルハンドラから呼べる（メモリのコピーと fsync だけ）
- `Display::request_verify` / `take_verify`: fb0 を読み戻して提示用バッファと比べる
  （ほかのプロセスに上書きされていないかの確認）
- `png::check_golden`: 正解画像と比べる。無ければ書く。`ZCODE_UPDATE_GOLDEN=1` で更新

### zc-input

- `Keyboard`（実機）と `Translator`（ロジック）を分けた。テストできる部分は全部
  `Translator` / `Repeater` / `Keymap` にある（時刻は引数で受け取る）
- `Keyboard::fds()` は 2 本（evdev と、リピート用の timerfd）。イベントループは
  evdev が読めたら `read`、timerfd が読めたら `on_timer` を呼ぶ
- タイムスタンプは `EVIOCSCLOCKID` で CLOCK_MONOTONIC にする（`zc_core::time::now_us`
  と同じ時計。遅延を引き算で出せる）
- リピート: 押下から 400ms、以後 30 回/秒。**上下の矢印・PgUp・PgDn は 20 回/秒**。
  Ctrl / Alt つき、Enter・Esc・Tab・F キーはリピートしない。最後に押したキーだけが
  リピートする。モディファイアが変わったら止める。処理が遅れたら溜めずに飛ばす
- リピート中は 8 回に 1 回 `EVIOCGKEY` で「まだ押されているか」を確かめる（離上を
  取りこぼしてもリピートが止まらなくなることがないように）
- `SYN_DROPPED`: 次の `SYN_REPORT` まで捨て、`EVIOCGKEY` で押下状態を取り直す。
  取りこぼした打鍵は作らない（勝手に文字が入るより、1 打鍵落ちる方がまし）
- キー配列は `keymap/cardputer-zero.toml`。**`build.rs` がビルド時に Rust の表に変換
  して埋め込む**（実機の実行ファイルに TOML のパーサは入らない。§8.1 のとおり）

### zc-font

- `Fonts`（メインが持つ。キャッシュあり）と `FontFiles`（mmap に触る処理だけ。`Send + Sync`）
  を分けた。`RasterMode::Assist` では `FontFiles` の処理を assist スレッドで走らせ、
  `RasterMode::Inline` ではその場で走らせる（render-test 用。結果が時間に依存しない）
- 鍵は「文字・書体の系統（`Face`）・大きさ（1/4 画素単位）・太字・斜体」。どのフォント
  にあるか（フォールバック）は assist 側で解決する（`cmap` も mmap の中にあるため）
- 等幅（`Face::Mono`）の全角は、半角 2 つぶんの幅になる大きさで描く
  （DejaVu 9px → 字幅 5 → CJK は 10px）
- 待ち時間: 1 字あたり最大 2ms に加えて、**1 フレームの合計で最大 6ms**（下の提案 5）
- 太字はいまは字形を太らせて作る。斜体は 12 度傾ける

### zc-ui と zcode

- `Widget::render(&mut self, cx: &mut RenderCx<'_>, area: Rect) -> Damage` と
  `invalidate()`（下の提案 1）
- `zcode::app`: `Screen`（画面ごとの処理）と `run`（イベントループ）。段階 2 の
  エディタ本体は `Screen` を 1 つ足す形で入る。ワーカーの結果は `AppEvent` に項目を足す
- `zcode::crash`: 異常終了の後始末（表は `crash.rs` の先頭）

## 3. design.md への提案

| # | 節 | 提案 | 理由 |
|---|---|---|---|
| 1 | §3 共通の約束 | 部品の形を `fn render(&mut self, cx: &mut RenderCx, area: Rect) -> Damage` にする（`RenderCx` = `Canvas` + フォント + 配色）。`fn invalidate(&mut self)` も持つ | 文字を描くにはフォント（キャッシュつき、`&mut`）が要る。`Canvas` だけを渡す形だと、部品がフォントを別の経路で握る必要がある |
| 2 | §3 構成 | `zc-core` の中身に「テキストの共通の型（`LineSource`・`TokenKind`・`Span`・`Theme`）」と「スレッドの受け渡し（`Worker`・`MainSender`・`TimerFd`）」を加える | 横同士の依存を禁じたまま、crate 間でやり取りするため |
| 3 | §4.2 | panic の扱いを書く: メイン・flush の panic は後始末して全体を止める。assist / batch / storage の依頼の中の panic は、その依頼だけを捨てて続ける | 補助の処理の不具合で、編集中の内容を道連れにしない |
| 4 | §4.3 | timerfd は 2 本（キーリピート用は `zc-input` が持つ。アプリ用は 1 本で複数の締め切りを扱う） | リピートのロジックを `zc-input` に閉じ込める |
| 5 | §5.4 | 「1 字あたり最大 2ms」に加えて「1 フレームの合計で最大 6ms」を入れる | 初めての字が多い画面（日本語のファイルを開いた直後）で、1 字ごとに待って 1 フレームが 145ms かかった（実測）。上限を使い切ったら残りは待たずに頼むだけにして、届いてから描き直す。入れた後は同じ画面で 19ms |
| 6 | §5.2 | 「テキスト 1 行（11 画素行）の変更で、実際に送られるのは約 12.9KB（3 ページ ≒ 19 行ぶん）」を前提に書く | ページ（4KB = 6.4 行）単位に丸められるため。実測。行の高さや位置をページ境界に合わせることはできない（6.4 行なので）が、見積もりは 19 行で行う |
| 7 | §6.2 | 上下の矢印も「画面がスクロールする操作」として 20 回/秒にする。モディファイアが変わったらリピートを止める。リピート中は `EVIOCGKEY` で押下を確かめる | 上下の矢印はスクロールを起こす。後ろ 2 つは誤動作の予防 |
| 8 | §6.2 | `KeyEvent` に `repeat: bool` を足す。`mods` に SYM / FN を参考情報として入れる | §2 の表のとおり |
| 9 | §6.2 | キーボードは sysfs の名前で探し、ほかの evdev デバイスは開かない | 全部の `/dev/input/event*` を開いて名前を調べると、起動に 60〜85ms かかった（実測） |
| 10 | §8.1 / §3 | 「実機の実行ファイルで TOML を読まない」をキー配列にも適用した（済）。ユーザーの設定（`~/.config/zcode/` の TOML）を実行時に読む段階では、下の §5「未解決」の 1 を先に片づける | fat LTO の aarch64 ビルドで、`toml` のパーサが異常終了した |
| 11 | §2 / §11.1 | APPLaunch は、ランチャー表示中は右上の時計と電池（行 2〜18）を描き続ける。SSH から起動した zcode の画面は、そこだけ上書きされる | 実測（下の §4.4）。APPLaunch からアプリとして起動したときにどうなるかは未確認 |

## 4. 実機での計測（2026-11-16）

条件: `measurements.md` と同じ実機・同じ常駐状態（labwc + APPLaunch のランチャー表示）。
zcode は SSH から `timeout` つきで起動。リリースビルド。数字は `zcode --stats` の出力
（時刻は CLOCK_MONOTONIC）。

### 4.1 フレームの所要時間（`zcode --bench <種類> --frames 200 --stats`）

単位は µs。「起床」は `poll()` から戻った時刻。

| 種類 | 描画 p50 / p95 | 行差分 + 受け渡し p50 / p95 | 起床 → flush に渡すまで p50 / p95 | 渡してから fsync を呼ぶまで p50 / p95 | 起床 → fsync を呼ぶまで p50 / p95 | fsync の所要 p50 / p95 |
|---|---|---|---|---|---|---|
| `line`（1 行 = 11 画素行、30ms 間隔、n=204） | 87 / 213 | 24 / 42 | 122 / 258 | 78 / 118 | **198 / 350** | 72 / 294 |
| `line-status`（1 行 + ステータスバー、n=205、fsync 403 回） | 125 / 323 | 34 / 57 | 172 / 361 | 153 / 289 | 322 / 687 | 321 / 1,060 |
| `scroll`（本文を 1 行ぶんずらす。変わるのは 124 行、50ms 間隔、n=205） | 109 / 206 | 116 / 178 | 241 / 410 | 278 / 454 | **513 / 789** | 113 / 832 |
| `full`（エディタ風の全画面を描き直す、n=204） | 400 / 632 | 125 / 187 | 540 / 836 | 105 / 220 | 655 / 1,017 | 76 / 1,046 |

- どの種類も、最大値は最初のフレーム（字形を待つ）で 7〜8ms
- `line-status` は 1 フレームで fsync が 2 回に分かれている（205 フレームで 403 回）。
  続けて呼ぶので fsync の所要が伸びる（p50 0.32ms、p95 1.06ms。measurements.md §1.2 と
  同じ傾向）が、**止まるのは flush スレッドだけ**で、メインの持ち時間は変わらない
- 1 打鍵ぶんの見積もり: 起床 → fsync を呼ぶまで 0.2ms（p95 0.35ms）+ fsync → 転送開始
  4.6ms（p95 6.5ms、measurements.md §1.1 の 13 行）+ SPI 転送 約 2.1ms（下の 12.9KB）
  ≒ **7ms（p95 9ms）**。キー押下 → evdev の区間は含まない（未計測）
- 全画面の描画 400µs は、measurements.md §2 の「全画面の文字合成 370µs（600MHz）」と合う

### 4.2 起動とメモリ

| 項目 | 値 |
|---|---|
| `main` → 最初のフレームを flush に渡すまで | **10〜12ms**（フォントがページキャッシュにあるとき） |
| 内訳 | キー配列 0.3〜0.5ms / キーボードを開く 0.4ms / フォントを開く 0.7〜1.3ms / fb0 を開いて画面を控える 1.2〜1.4ms / 最初の描画と受け渡し 7〜8ms |
| 直す前（全部の evdev デバイスを開いて名前を調べていた） | 72〜109ms（うちキーボードを開くのに 60〜85ms） |
| RSS | 5.9〜6.3MB（キー確認・計測）、8.4MB（フォント比較の全ページを表示した後） |
| スレッド | 3 本（メイン・flush・assist） |
| 待機中の CPU | 5 秒間で 0 tick（1 秒ごとの表示更新だけの状態） |
| 実行ファイル | 1.87MB |

再起動直後（フォントが SD にしか無い状態）の起動時間は測っていない。

### 4.3 初めての字が多い画面

`zcode --fonttest --page 5`（プロポーショナル。最初のフレームで約 300 字を作る）:
1 フレームの合計の上限を入れる前は最初の描画に 145ms、入れた後は 19ms
（残りは届いてから描き直す）。

### 4.4 APPLaunch による上書き

| 項目 | 値 | 方法 |
|---|---|---|
| zcode を動かしていないときの SPI 送信量 | 17.9kB/秒 | `/sys/class/spi_master/spi0/statistics/bytes_tx` を 5 秒 |
| zcode が待機中（1 秒に 1 回ステータスバーだけ更新） | 26.9kB/秒 | 同上。増えた 9kB/秒は zcode の分（11 行 → 2 ページ = 8.2KB） |
| fb0 の読み戻しで、zcode の内容と違っていた回数 | 34 / 38、45 / 46、12 / 12（どの実行でもほぼ毎回） | `--watch-fb 200〜500` |
| 違っていた行 | 行 2〜18（最大 16 行） | 同上 |
| 上書きの中身 | ランチャー右上の時計と電池残量の表示 | 実行中に fb0 を読み出して画像にした |

- **SSH から起動した場合、APPLaunch は再描画を止めない。** 時計と電池の部分だけを
  描き続けるので、zcode の画面の右上（タブバーの右端）が上書きされる
- APPLaunch からアプリとして起動した場合（.desktop 経由）にどうなるかは、インストール
  （sudo）が要るので未確認。既存の Python アプリ（qrreader など）は APPLaunch から
  起動して画面を占有できているので、止まる可能性が高い
- 画面の復元の確認（終了後の fb0 を起動前と比べる）では、この時計の部分だけ、
  分が変わったときに違いが出る

### 4.5 後始末の確認

| 終わり方 | 結果 |
|---|---|
| 無操作で自動終了（`--idle`） | 終了コード 0。fb0 は起動前と同じ。キーボードの独占は外れている |
| SIGINT / SIGTERM / SIGHUP（`timeout -s`） | ふつうに終了（統計とログの最後の行まで出る）。fb0 は同じ。独占は外れている |
| メインの panic（`--bench panic`） | 終了コード 101。fb0 は同じ。独占は外れている |
| メインが固まる + SIGINT（`--bench hang`） | 2 秒後に SIGALRM のハンドラが後始末して終了。fb0 は同じ。独占は外れている |
| 実行中の独占 | 別のプロセスから `EVIOCGRAB` を試すと EBUSY（独占できている） |

確認の方法: 起動前と終了後に `dd if=/dev/fb0` で読んで比べる。独占は、別のプロセスから
`EVIOCGRAB` を試して確かめる。

### 4.6 そのほか

- 実機で描いた PNG（`--render-test`）は、開発コンテナ（x86_64）で作った正解画像と
  1 バイトも違わない（キー確認・フォント比較 2 ページ目で確認）。render-test は
  開発コンテナだけで足りる
- DejaVu Sans Mono の字幅（`0` の送り幅を丸めた値）: 8px → 5、9px → 5、10px → 6、
  11px → 7、12px → 7。エディタ全幅（行番号 3 桁）で 9px は 60 桁 × 13 行、
  10px は 49 桁 × 12 行、11px は 42 桁 × 11 行

## 5. 未解決・要確認

1. **fat LTO の aarch64 ビルドで `toml` 0.8.23 のパーサが異常終了した。**
   キー配列を実行時に `toml::from_str` で読んでいた時点のあるビルドで、起動直後に
   `memory allocation of 8872158475505001842 bytes failed`（中身は TOML の本文の一部を
   長さとして読んだ値）で abort した。スタックは `Keymap::parse` →
   `winnow::error::StrContextValue` の `Display`（パースエラーの文字列化）。
   - 同じソースの x86_64 リリースビルドは正常。aarch64 でも `lto = "thin"`、
     `lto = "off"`、`opt-level = 1` は正常。fat LTO + `opt-level = 3` のときだけ起きた
   - 関係ない箇所のコード（計測用の数行）を足す前のビルドでは起きなかった。`toml` で
     同じファイルを読むだけの小さなプログラム（同じプロファイル）でも起きなかった
   - 原因は特定できていない（`toml` / `winnow` の中の未定義動作か、コンパイラの
     誤コンパイル）。こちらの `unsafe` は、その経路では `clock_gettime` しか通らない
   - 対処: キー配列はビルド時に表へ変換し、**実機の実行ファイルから `toml` を外した**。
     ユーザーの設定を実行時に TOML で読む段階になったら、先に原因を調べるか、
     プロファイルを `lto = "thin"` にするかを決める
2. **Sym レイヤーの刻印 → キーコード**（キー確認モードでユーザーと確定する。§6）
3. **キー押下 → evdev の遅延**: ソフトウェアだけでは測れない（カーネルのタイムスタンプは
   ドライバが I2C を読んだ後に付く）。キー確認モードで測れるのは「カーネルのタイム
   スタンプ → 読み取り → fsync」。押下からの遅延は、液晶とキーを一緒に高速度で撮る
   などの外からの計測が要る
4. **ドライバが Shift / Sym / Fn をどう送るか**（押しっぱなし・ワンショット・ロックで、
   モディファイアのキーコードの押下・離上が来るのか）。キー確認モードのログで分かる。
   来ないなら、Shift の状態をこちらで追えないので、`Mods::SHIFT` の付け方を決め直す
5. **APPLaunch からアプリとして起動したときに、時計・電池の再描画が止まるか**
6. **フォントの大きさと行の高さ**（`zc_ui::layout::CODE_PX` / `CODE_LINE_H`）。
   フォント比較画面をユーザーに見てもらって決める。CJK はヒンティングなしで線が薄く
   見えるので、濃度を持ち上げる補正（ガンマ）を入れるかも合わせて判断する
7. **本物の太字**（DejaVu Sans Mono Bold / Noto Sans CJK Bold を別に開く）。いまは
   字形を太らせている（段階 2 の `zc-font`）
8. **BDF**: 読めるのは `ENCODING` が Unicode のものだけ。東雲（JIS X 0208）は変換が要る。
   実機にビットマップフォントが無いので、見比べはまだしていない
9. `cargo clippy` の警告が十数件残っている（引数の数、rustdoc の書き方など。動作に関係なし）

## 6. キー確認の進め方（ユーザーと行う）

準備（メインのセッション）:

```sh
# 開発コンテナ: cd zcode; ..\container\dev.ps1 ./build.sh
scp zcode/out/zcode <実機>:/tmp/
```

どの実行も `timeout` を付ける。終了は **Esc を続けて 5 回**（無操作でも終わる）。

### 手順 1: 刻印の対応表（`--guide`）

```sh
ssh <実機> 'rm -f /tmp/zcode-keytest.jsonl; timeout -s INT -k 5 900 /tmp/zcode --keytest --guide --idle 300 --stats'
```

画面の下に「刻印 `!` のキーを押す 1/32」と出る。ユーザーは:

1. その記号が刻印されているキーを、**その記号が出る押し方で**押す
   （Sym を押しながら、Shift を押しながら、など。刻印のとおりに）
2. その記号がキーボードに無ければ **Enter**、押し間違えたら **BackSpace** で 1 つ戻る
3. 32 個（`` ! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ ` { | } ~ ``）が
   終わると、ふつうのキー確認の表示に戻る。**Esc を 5 回**押して終わる

### 手順 2: モディファイアの送られ方と遅延

```sh
ssh <実機> 'timeout -s INT -k 5 900 /tmp/zcode --keytest --idle 300 --stats'
```

ユーザーに、次の順で押してもらう（画面の `mods` と右下の札、`map` の列を見る）:

1. `a` を 1 回。次に `a` を 2 秒押しっぱなし（リピートが `×N` と数えられる）
2. Shift を**押しながら** `a`。次に Shift を**1 回タップしてから** `a`、もう 1 回 `a`
   （ワンショット）。次に Shift を**2 回タップしてから** `a` を 2 回（ロック）、
   Shift をもう 1 回タップ（解除）
3. 同じ 3 通りを Sym + `r`、Fn + `5` で
4. Ctrl を押しながら `s`、Alt を押しながら `b`、Ctrl + Shift を押しながら `k`
5. Fn をロックして、矢印（Fn + `f` / `z` / `x` / `c`）を 2 秒ずつ押しっぱなし
6. できるだけ速く 10 打鍵（取りこぼしと `dropped` の確認）
7. Esc を 5 回

### 手順 3: ログを取り込む

```sh
scp <実機>:/tmp/zcode-keytest.jsonl zcode/out/
ssh <実機> 'rm -f /tmp/zcode /tmp/zcode-keytest.jsonl'
# 開発コンテナで:
cargo run -p zcode -- --keymap-from-log out/zcode-keytest.jsonl
```

出てくる行（`{ code = 71, key = "&", layer = "sym", pos = [1, 3] },` の形）で
`keymap/cardputer-zero.toml` の該当行を置き換え、`provisional = true` を消す。
「答えに出てこなかった未確定のキーコード」は、刻印が記号でないキー（かな系など）なので、
ユーザーに刻印を聞いて決める。直したら `cargo test -p zc-input`（埋め込みの表の検査）。

ログの 1 行は 1 イベント（`"type":"ev"`）で、`t_kernel_us` / `t_read_us` /
`t_fsync_us`（どれも CLOCK_MONOTONIC の µs）、`scan`（MSC_SCAN）、`mods`、`down`、
こちらの解釈（`map`）が入る。手順 2 の結果から、次を `measurements.md` に足す:

- 読み取りの遅れ（`t_read_us - t_kernel_us`）と、fsync までの遅れ
  （`t_fsync_us - t_kernel_us`）の分布
- モディファイアの押下・離上が、押しっぱなし / ワンショット / ロックのそれぞれで
  どう届くか
